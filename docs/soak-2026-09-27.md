# Soak, load, chaos and fairness re-run (2026-09-27)

Task rows M6-C176 and M6-C150. This re-runs every experiment in
[soak-2026-09-26.md](soak-2026-09-26.md) on a head that contains the fixes made
since: `TCP_NODELAY` (M6-C124, M6-C163, PR #195), the device staying online under
load (M6-C151, M6-C159, M6-C160, PR #199), and the soak harness's MCP session
accounting (M6-C146, PR #203). The 2026-09-26 document is kept as measured, as the
record of the builds it measured. Where its figures are superseded, it now
points here.

These are **measurements, not service levels.** The same limits apply as before.
Each experiment ran on one 4-vCPU GitHub runner that hosted the relay, the Redis
TLS forwarder, the devices and the Python load generator together. It used one
device (two for fairness) and one tenant. Neither the 20 users × 5 devices case,
the 100 devices over 24 hours case nor the 1 GiB transfers in
[testing.md](testing.md#soak-chaos-and-load-experiments) were run.

and 0 rotations. Chaos is too short to cross a 300 s rotation.

**No silent replay and no fake success,** measured again in both runs:

* 0 integrity mismatches.
* MCP backend invocations were 3,117 and 3,089, exactly the consumer-visible
  successes (3,116 and 3,088) plus one warm-up. No request reported as unknown
  or refused executed, and nothing ran twice.
* Every non-success carried an explicit code and execution class. The
  exceptions are the 6 transport-level `CONN_ConnectionResetError` rows during
  the relay restart and the MCP `-32600` rows below.

**What changed for MCP during outages.** An MCP call to an offline device is
now answered `DEVICE_OFFLINE`/not_dispatched, like echo: 0 `NOT_FOUND` in either
run. On 2026-09-26 it was `NOT_FOUND` (M6-C123). This re-run did not attribute

worker's first call on its old MCP session got HTTP `404` with JSON-RPC

end with the device session, and a `404` on an unknown session is the MCP
transport's signal to re-initialise. The harness does re-initialise: the pool
counts the forgotten session, and the next call succeeds. These are therefore
expected session losses, not errors of the product. No probe session was left
open at shutdown: neither run emitted an `mcp-session-leak` event.

## 6. Attribution of M6-C182 and M6-C183 (2026-09-27, branch `fix-c182-c183`)

Sections 2 and 4 are kept as measured. This section attributes them, as far
as one shared host allows. The harness gained payload-free attribution:
* CPU per process per step or phase: relay, forwarder, devices and the
  driver, plus the Redis server's `INFO` CPU and script counts.
* The driver event loop's scheduling lag: how late a 10 ms sleep wakes.
* The relay's new single-actor load metrics. The rate of
  `tunnel_relay_actor_busy_microseconds_total` is a **lower bound** on the
  actor's busy fraction, because only its command branch is timed.

Fairness now also times user B from a separate `client` process with its own
event loop, beside the in-loop B, in the same phase. Both of B's clients
connect before the flood starts. Three new options:
* `--generator-processes` moves load workers into client processes.
* `--flood-processes` moves A's fairness flood into client processes.
* `--honor-retry-after` makes workers honour a `CONNECTION_LIMIT` refusal's
  `retry_after_ms`.

The same 4-vCPU hosted runner still hosts everything. No experiment here is
off-host, and runners differ, so figures are compared only within one run.

* **The old harness inflated B by about 4× in its own setup, but the
  interference is real.** With A's 128 workers on the same asyncio loop as B,

  refusals a second, where the same 128 workers in two processes made 695.

  **90.77 ms** against a 5.26 ms baseline: about **17×**. On the shared device
  it was 98.3 ms. So a flood that does not back off reproduces the full
  interference, even with B measured properly.
* **The interference depends on how the flooder behaves.** With the same
  two-process flood honouring `retry_after_ms`, refusals fell to 67 a second
  and A was served at 1,806 OK/s. B's p50 was then 29 ms, about 6× its
  baseline and about A's own p50 of 32 ms.
* **How the interference splits between relay refusal cost and host
  contention is not attributed.** In the run without back-off the 4 vCPUs
  were saturated: relay 145%, flood processes about 137%, forwarder 27%,
  device 22% and Redis 28% of one CPU. The relay's per-refusal cost (M6-C194)
  and plain CPU contention cannot be separated on one host.
* **The single relay actor's timed busy fraction was low.** It was 9.2 --
  9.5% during the driver-loop floods and at most 21.4% at 1,806 OK/s. This is
  a lower bound, so it does not show the actor is idle. It does make the actor
  an unlikely sole bottleneck. Redis was 26 -- 59% of a CPU at 37 -- 48 µs per
  script call.
* **Requests share resources with no per-user scheduling.** Requests from
  every user share one Tokio runtime, one Redis connection and one host, in
  arrival order. Whether a per-user share is needed is an owner decision

### M6-C182: why served throughput fell above 64 connections

Echo, closed loop, 30 s steps. Figures are OK/s, with CPU in percent of one

* **The drop needs clients that do not back off.** When workers wait the
  refusal's `retry_after_ms` (1 s), the served rate holds at 96 and 128
  workers:
  * Echo, run 36267311313: 1,426, then 1,362 and 1,360 OK/s, within 5% of
    the 64-worker figure.
  * MCP, run 36269590574: 1,242, then 1,216 and 1,184 OK/s, within 5%.

  Every MCP step had `opened` = `deleted` and 0 unaccounted sessions. The MCP
  `ADMISSION_LIMIT` and `HTTP_DEADLINE_EXCEEDED` rows are the documented
  per-owner bound and M6-C181.

  Without back-off, echo falls by a half to two thirds, whether the generator
  shares the driver loop or runs in four processes.
* **This is not only a generator artefact: the cost is split.** Refused
  connections complete a TLS handshake on both sides. In run 36266360839,
  going from 64 to 96 workers added about 90 points of generator CPU and 12
  points of relay CPU, while served requests fell by 1,313 a second.
  * At 96 workers, about **67% of the relay's CPU went to refusals**. The
    relay used 155% of a CPU. Its 732 served requests a second account for
    about 51 points at 0.70 ms each. The rest, about 104 points over 926
    refusals a second, is about 1.1 ms per refused connection.
  * The per-served-request cost is 0.70 ms in run 36266360839 (142.8% at
    2,045 OK/s) and 0.79 ms in run 36267862335 (142.1% at 1,806 OK/s).
  * The per-refusal estimate is 1.1 ms in run 36266360839 and 1.4 ms in run

  These are differences on a saturated host, so they are approximate. The

* **The 64-worker plateau of about 1,530 OK/s was partly the driver loop.**
  In one run, four generator processes reached 2,045 OK/s. In another,
  36267311313, they reached 1,426. Runners differ.

### Also seen: a long rotation freeze with ambiguous outcomes (M6-C195)

Run 36267862335, shared-device flood phase (`--flood-processes 2
--honor-retry-after`, A at 1,456 OK/s):
* A data rotation stayed open from 47.2 s into the phase until after the
  phase ended. The relay samples show `sessions_rotating` 1, 5 device
  sockets, 35 streams and 12,288 queue bytes, unchanged from 48.6 s to
  73.7 s.
* The shared device refused 34,403 requests `ROTATION_FREEZE`.
* 35 requests started at 47.20 -- 47.21 s ended
  `REVERSE_CHANNEL_INTERRUPTED` with execution `unknown`, each after 30.0 s
  (30,009 -- 30,018 ms). Two of them were user B's off-loop requests. That
  30 s wait explains the phase's overrun of about 18 s. It also explains the
  126 requests the off-loop B never sent (474, not 600), since its rate loop
  was blocked. B's in-loop client was refused `ROTATION_FREEZE` 126 times.
* 9 requests got `DEVICE_REJECTED`/not_dispatched.
* The device process never restarted.

A flood by one user left another user's requests with **ambiguous
outcomes**. This is the kind of long freeze M6-C161 could not explain,
recurring. Its mechanism is not measured here.
