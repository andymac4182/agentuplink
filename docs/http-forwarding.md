This document defines **`http-forward/1`**, an internal Agent Tunnel encoding; it is not a new public HTTP or ACP standard.

The intended route is **cloud agent → Agent Tunnel's Axum API → optional owner HTTP/3 hop → existing device data WebSocket → desktop adapter**. Responses follow the reverse route. The desktop adapter can be an in-process ACP HTTP-to-stdio service, an MCP bridge, or a typed CUA HTTP facade. The client CLI opens the device connections; no public inbound desktop port is required.

Read [runtime.md](runtime.md), [cluster.md](cluster.md), and [protocol.md](protocol.md) for authentication, owner fencing, admission, outer frames, credits, and socket rotation. This encoding preserves HTTP request/response structure; adapter documents retain authority over their application lifecycles and permissions.

## One exchange, one stream

An authorized `OPEN` selects a fixed device export, its application compatibility profile, and `http-forward/1`. The accepted context binds tenant, principal, device, service, owner token, grant version, operation/request IDs, deadline, and negotiated byte limits. These authoritative fields are outside the HTTP heads. The caller cannot override them with HTTP headers, JSON fields, paths, or an embedded URL.

One admitted logical stream contains exactly one HTTP request in the owner→device direction and one HTTP response in the device→owner direction. A second HTTP request needs a new stream. A long-lived SSE GET keeps its stream; concurrent ACP POSTs get separate streams bound to the same independently authorized ACP connection. There is no HTTP pipelining or request multiplexing inside one logical stream.

The owner and device run this codec after the outer protocol has ordered and deduplicated DATA payloads. Bytes from successive DATA frames form a continuous byte stream in each direction. Record headers/payloads may cross DATA frames, and one DATA frame may contain several records. Outer WebSocket, HTTP/3, and DATA boundaries never define HTTP body or JSON-RPC message boundaries.

The cluster peer route wraps these records in its independently authenticated admission envelope. It preserves ordered request/response bodies and uses no new HTTP/3 route or arbitrary destination. An owner remains the sole authority for tunnel sequences. Consumer credentials may reach the owner for independent verification as specified in the cluster contract; they never appear in the device's HTTP heads.

## Exact v1 record encoding

Each record begins with this fixed eight-byte header. Integers use unsigned network byte order. `payload_length` excludes the eight-byte header.

| Offset | Bytes | Field |
| --- | ---: | --- |
| 0 | 1 | Record kind |
| 1 | 1 | Flags, exactly zero in v1 |
| 2 | 2 | Reserved, exactly zero |
| 4 | 4 | Payload length |
| 8 | Declared length | Payload |

| Kind byte | Name | Payload |
| --- | --- | --- |
| `0x01` | `REQUEST_HEAD` | Bounded UTF-8 JSON request head |
| `0x02` | `RESPONSE_HEAD` | Bounded UTF-8 JSON response head |
| `0x03` | `BODY` | 1–65,528 raw body octets; no base64 or JSON escaping |
| `0x04` | `END` | Exactly zero bytes |

The maximum complete record is 65,536 bytes, fitting the default DATA payload ceiling when unsplit. HEAD payloads have the smaller 16 KiB cap below. Reject unknown kinds, nonzero flags/reserved bytes, invalid kind-specific lengths, and allocation overflow immediately after reading the fixed header. The selected application encoding supplies the version; no redundant magic, stream ID, or application sequence number is added inside each record.

For example, the BODY record containing ASCII `hello` is:

```text
03 00 00 00 00 00 00 05 68 65 6c 6c 6f
```

The END record is always:

```text
04 00 00 00 00 00 00 00
```

The incremental decoder retains at most one unfinished eight-byte record header, one bounded HEAD, or one bounded BODY fragment. It must stream BODY fragments into credited downstream buffers; it must not collect the entire HTTP body before emitting it. Partial records have a fixed completion deadline and share the stream's queue/byte budget.

### Request head schema

All fields below are required; there are no additional fields in v1:

```json
{
  "method": "POST",
  "path": "/acp",
  "query": "",
  "http_version": "2",
  "headers": [
    ["content-type", "application/json"],
    ["accept", "application/json, text/event-stream"],
    ["acp-connection-id", "connection-demo"],
    ["acp-session-id", "session-demo"]
  ],
  "body_length": null
}
```

`method` is one of `GET`, `HEAD`, `POST`, `PUT`, `PATCH`, `DELETE`, or `OPTIONS`, restricted further by the selected route; `path` is a canonical path within the selected local service; `query` is the validated query component without `?`; `http_version` is the accepted consumer HTTP version (`"1.1"` or `"2"`), not the peer protocol. The ingress derives that version from its HTTP connection. ACP's HTTP/2 requirement is checked before admission and again against the selected profile.

`headers` is an ordered array of exactly two-string arrays, preserving separately allowed repeated field values. `body_length` is either `null` for an unknown streaming length or a canonical unsigned decimal string (`"0"` or a nonzero first digit followed by decimal digits), at most `u64::MAX`. No signs, leading zeros, floating point, or JSON-number coercion. Every request also has a finite configured cumulative body limit regardless of this field.

### Response head schema

All fields are required, with no additional fields:

```json
{
  "status": 200,
  "headers": [["content-type", "text/event-stream"], ["cache-control", "no-store"]],
  "body_length": null
}
```

`status` is an integer from 200 through 599. There is exactly one final response head. No reason phrase, raw status line, or informational 1xx record is carried. The ingress handles `Expect: 100-continue` locally after authorization/admission; backend 100/103 responses are consumed locally. A 101 upgrade, CONNECT, or protocol switch is unsupported by this profile and must fail before establishing a different tunnel.

`body_length` describes **actual response body bytes**, not a selected representation's hypothetical size. Responses to HEAD and status 204, 205, or 304 require `"0"`, no BODY, and END. Omit forwarded Content-Length metadata for these responses in v1: the device adapter drops a handler's representation-size Content-Length on a HEAD or 304 response rather than forwarding it, accepts only `0` on 204 or 205, and still rejects any actual body bytes. Applications requiring the representation-size hint need an explicit extension. Ordinary response lengths follow the request head's decimal-string rules.

JSON heads must be one object, contain valid UTF-8, and reject duplicate keys, unknown keys, invalid types, and trailing non-whitespace data. Require valid Unicode scalar values when decoding escapes. Do not rely on a deserializer that silently accepts duplicate keys or replaces invalid text. Whitespace and object-key order are insignificant; JSON serialization need not be canonical because identity is bound through authenticated admission rather than head signatures.

## Directional state machine

The successful grammar is:

```text
owner → device: REQUEST_HEAD, BODY*, END, outer FIN
device → owner: RESPONSE_HEAD, BODY*, END, outer FIN
```

| State | Accepted input | Transition |
| --- | --- | --- |
| `AwaitHead` | Correct head for this direction | Validate all fields and policy, then `Body` |
| `Body` | Nonempty BODY | Stream bytes, update checked counters, remain `Body` |
| `Body` | END | Check declared/actual length and body restrictions, then `AwaitFin` |
| `AwaitFin` | Outer ordered FIN, with no extra data | Mark direction complete |
| Any unfinished state | Outer RESET or unrecoverable carrier failure | Mark direction interrupted; preserve known dispatch state |

A second head, wrong-direction head, BODY before HEAD or after END, repeated END, record bytes after END, FIN before END, or EOF within a record is a protocol error. FIN must follow the final DATA containing END in sequence order, has no HTTP-record payload, and consumes the outer protocol sequence as usual. Request FIN half-closes only the request; it does not close the response stream or cancel the operation.

Directions progress independently. A backend may begin a final response after request HEAD and before the upload ends; the bridge must read/write both directions concurrently. This is essential for streaming and early rejection. An early response does not by itself claim request-body completion. Continue bounded upload forwarding or discard under the adapter's explicit rejection policy. If the response fully completes first, the request sender may reset an unfinished upload; preserve the already completed HTTP response while aborting remaining request work. Never fabricate a successful request END for bytes that were not received.

Do not dispatch an unvalidated head. The initial JSON-command profiles for ACP, MCP, and typed CUA additionally wait for their complete bounded request body and schema/policy validation before invocation; generic HTTP framing alone cannot authorize a partially parsed command. This is a selected-profile policy, not a universal requirement that every MCP HTTP request be buffered. A profile permitting streaming request dispatch must declare its partial-write/cancellation semantics, validation boundary, and budget before forwarding early body bytes to a mutating backend.

## Paths, headers, and HTTP normalization

This is a fixed-export bridge, not a general reverse proxy. The public route maps to a configured local service path. `path` has at most 1,024 ASCII bytes, starts with exactly one `/`, and uses only `/`, ASCII alphanumerics, `-`, `.`, `_`, and `~`. Reject empty, `.`/`..` segments, repeated slashes, backslashes, percent escapes, query/fragment delimiters, absolute URLs, authority forms, and NUL. `/` alone is valid only if that export declares it. The complete method/path pair must match an advertised route; filesystem names and user data belong in the adapter's typed body/parameters rather than a path splice.

`query` is empty unless the service profile names allowed query parameters. Maximum 2 KiB and 32 pairs; validate percent escapes and decode exactly once for policy checks. Reject invalid UTF-8 or decoded controls, unrecognized keys, credential-bearing parameters, and duplicates unless that specific parameter permits them. Preserve the accepted original query bytes for the target; downstream code must not perform a second authorization decode. A query cannot select another service, backend address, executable, or workspace.

Header names are lowercase ASCII HTTP token characters, 1–128 bytes. Values contain printable ASCII or horizontal tab only, at most 4 KiB; reject CR, LF, NUL, other controls, and obsolete folded lines. Trim boundary optional whitespace once at ingress. Permit at most 32 field entries and 8 KiB of total decoded name/value bytes, including repeats; the serialized head must still fit 16 KiB. Singleton fields must occur once; accepted list/repeated semantics belong to the profile, never generic comma concatenation.

Apply direction-specific header allowlists at ingress, owner, and device. Candidate fields include content type, accept, cache policy, request conditions, and the selected ACP/MCP version/session metadata. The implementation PR must enumerate the actual set for each pinned application profile. An unknown application header fails validation; it is not silently treated as supported.

Never pass HTTP routing/framing authority or credentials through this array: `host`, `connection` and every field it nominates, `keep-alive`, `proxy-connection`, `transfer-encoding`, `te`, `trailer`, `upgrade`, `expect`, `content-length`, `authorization`, `proxy-authorization`, `cookie`, `set-cookie`, forwarded identity headers, or `x-agent-tunnel-*` internal metadata. Public-layer OAuth challenges, browser cookies/CORS, and operation-ID headers are constructed by the authenticated ingress layer. Adapter-owned backend credentials are inserted locally from fixed configuration. Do not forward private backend WWW-Authenticate challenges as if they were relay login instructions.

The HTTP libraries validate their own message framing before the bridge strips transport headers. Reject conflicting/duplicate Content-Length and conflicting Transfer-Encoding/Content-Length requests before dispatch rather than laundering them through normalization. Decode HTTP transfer framing into body octets once; never copy chunk-size lines into BODY. Validate any incoming Content-Length against the actual bytes and carry its checked length as `body_length`. The receiving HTTP adapter may generate its own Content-Length or streaming framing from that typed value; it must not copy consumer framing verbatim. [HTTP field forwarding and length semantics](https://www.rfc-editor.org/rfc/rfc9110.html#section-7.6.1), [HTTP/1 message framing](https://www.rfc-editor.org/rfc/rfc9112.html#section-6.3)

No trailer records exist in v1. Reject declared trailers before dispatch; a nonempty trailer discovered during body reading causes a scoped reset rather than silently dropping potentially meaningful metadata. For the initial profiles accept identity content encoding only, request identity from fixed HTTP backends, and reject unsupported encodings. This prevents hidden decompression from changing body limits or byte counters. Other encodings require an explicit bounded profile.

Never follow backend redirects automatically. A permitted Location value must be mapped to a public route within the same authorized export; private addresses, credentials, or cross-service targets are errors. Fixed local HTTP services use operator-configured targets and no caller-supplied host/proxy settings. In-process desktop handlers construct typed Rust HTTP requests directly and require no local listener.

## Backpressure, streaming, and deadlines

BODY data is raw binary; preserve byte order and content exactly. For SSE, forward its headers and body bytes incrementally without parsing/reformatting events, inserting synthetic events, joining complete messages, or waiting for END. Body chunks may split UTF-8 characters, JSON, SSE lines, and blank event delimiters. The application/SSE parser consumes the reconstructed HTTP body. Flush available output promptly; proxy response buffering/compression must be disabled for the deployed streaming route.

Every record byte, including headers and HEAD JSON, is charged to the existing directional credits and device/session budget. Per-hop pending queues also obey [cluster.md](cluster.md): initially 256 KiB per peer stream, 8 MiB per peer connection, and bounded request counts. The HTTP adapter has no independent unbounded body/event queue. Read upstream only with downstream capacity; do not issue WINDOW_UPDATE merely because bytes moved to another queue that remains charged. A replay of an existing outer sequence consumes no new logical credit.

The common profile requires concrete per-request request/response cumulative byte limits and a wall-clock deadline at admission. Known lengths above the selected limit fail before BODY allocation. Streaming responses may have a larger configured cumulative limit than finite JSON responses, but no unlimited sentinel is allowed. The adapter chooses useful finite limits and reports them in service discovery; the lower deployment/global limits still apply.

Starting transport progress budgets: first HEAD within 10 seconds after OPENED, a partly received record completed within 10 seconds from its first byte, output-credit stall bounded to 30 seconds, and FIN within 10 seconds after END. HEAD/record/FIN progress clocks pause only while this endpoint's recorded rotation freeze prevents sending, or while this receiver has deliberately withheld credit; the independently bounded overlap/credit-stall timers keep those pauses finite. The absolute application deadline never pauses. Application silence between records is governed by the ACP/MCP/CUA profile; an SSE connection is not killed merely because it has no current event. These values are configurable with hard ceilings. Trickled bytes do not restart progress budgets, and unrelated heartbeats do not extend them.

Reserve bounded control capacity for cancellation, reset/error handling, drain acknowledgments, and terminal status. A credit-stalled BODY cannot prevent the owner from processing cancellation. Do not hold a shared mutex across socket, HTTP-body, or child-process I/O; supervise separate directional pumps with one exchange owner and explicit shared terminal state.

## Cancellation, resets, and execution uncertainty

Use the outer tunnel `RESET` exactly as defined in [protocol.md](protocol.md): one unsigned 16-bit reason code in network byte order, using the shared reason-code registry. There is no JSON reset payload and no extra HTTP error/reset record. HTTP forwarding uses the protocol's applicable adapter-failure/cancellation reason; HTTP-specific detail belongs in bounded `RESULT_STATUS` metadata and the scoped operation-status lookup, not a private numeric extension to RESET.

HTTP error detail uses a `code` chosen from `HTTP_BAD_RECORD`, `HTTP_INVALID_HEAD`, `HTTP_BODY_LIMIT`, `HTTP_LENGTH_MISMATCH`, `HTTP_UNSUPPORTED_FEATURE`, `HTTP_STREAM_INTERRUPTED`, `HTTP_CANCELLED`, or `HTTP_DEADLINE_EXCEEDED`, plus `execution` equal to `not_dispatched`, `dispatched`, or `unknown`. Limit this adapter-specific detail to 512 serialized bytes inside the normal bounded status envelope. It reports the emitting endpoint's knowledge; only the device's authoritative dispatch record can prove a command did not run. An ingress that lost the acknowledgment reports `unknown`, not `not_dispatched`. No HTTP bodies, arbitrary backend errors, private paths, or credentials belong in control/status metadata.

On local cancellation/error, stop local adapter delivery and unfinished pumps immediately, retain the terminal tombstone, and send a scoped control `CANCEL` promptly where remote cancellation is needed. `RESULT_STATUS` reports the actual or unknown outcome independently. Queue the outer RESET through the owner actor: it consumes a sequence, remains ordered behind previously assigned DATA/FIN, and participates in fences, ACKs, and replay. Reserved terminal capacity bypasses application-byte-credit exhaustion, **not sequence order or a rotation freeze**. Control cancellation can therefore stop work before the queued RESET reaches the peer.

Retain receive cursors, emitted frames, and drain-roster references until protocol-driven `STREAM_FORGET` permits reclamation. Consume/account for pre-reset in-flight peer frames in sequence as terminal discard without delivering them to the adapter. A received RESET triggers the local terminal response at most once as specified by the protocol. Resetting during rotation cannot erase a fence gap; crossed resets cannot resurrect a stream or overwrite a stronger known application result.

Consumer disconnect maps to bounded best-effort application cancellation plus RESET for unfinished exchanges. The ingress records a consumer that releases the response body after its head as its own outcome, `released`, rather than as an ordinary abort (M3-32): the relay does not interpret bodies, so it cannot tell a release after the application's final message (an MCP client drops a POST's SSE stream once the final JSON-RPC response has arrived) from one in the middle of it, and the device's record — which saw whether its response completed before the RESET arrived — is authoritative for the call, as its dispatch record is for execution. The RESET and `HTTP_CANCELLED` are unchanged, so a handler still running is told. A consumer that leaves before any response head is recorded at the ingress as well (M3-14). Cancellation of a response body is protocol-sensitive: current MCP and legacy MCP have separate rules, and an ACP GET loss has the connection cleanup policy in [acp.md](acp.md). `session/cancel` and permission responses are ordinary separately admitted ACP POSTs, not an HTTP forwarding codec feature. Request FIN and scheduled physical-socket closure never synthesize those messages.

Before public response headers are committed, a failure attributable to the consumer's own request is an ordinary 400, 413, 417 or 501 with the same sanitized metadata; a forwarding failure can become a scoped 502, 503, or 504 gateway response with sanitized Agent Tunnel error metadata. After headers/body begin, fail/reset that HTTP stream; never append a forged JSON-RPC error or successful SSE event to its body, and never turn truncation into an ordinary successful END. The host may already have seen partial output; the separate operation facility reports actual or unknown outcome. A completed HTTP response remains completed if only the unfinished upload is subsequently aborted.

Outer ACK, receipt of HEAD, HTTP 200/202, response END, and child/tool completion are distinct facts. The bridge records admission, dispatch, and HTTP completion separately from application outcome. No retry may reopen an HTTP exchange after forwarding could have reached the device. In particular, a GET may allocate an ACP subscriber or trigger application behavior; this codec does not infer retry safety from the method name. Only explicit adapter semantics plus proved `not_dispatched` permit an admission retry. Never replay an ambiguous prompt, tool call, write, or click under a fresh operation ID.

## Rotation and recovery

During scheduled handover, freeze old-generation DATA/FIN/RESET assignment, retain partial codec state and bounded pending bytes, drain through the immutable per-stream fences, commit the replacement, and resume the same stream/counters. HEAD does not repeat. BODY may resume partway through a record. END, FIN, and RESET queued during quiescence wait behind their preceding sequences and are sent only on activation or an explicit coordinated abort. Local cancellation and bounded control CANCEL/RESULT_STATUS remain available during freeze; closing the old physical socket has no HTTP completion meaning.

**A new exchange that arrives during a freeze is held, not refused** (task row M3-15; owner decision, 2026-09-25). New stream admission is paused from QUIESCE until COMMITTED or the attempt's end ([protocol.md, "Quiesce admission"](protocol.md#scheduled-handover-prepare-fence-drain-commit-retire)). The owner holds the new exchange's OPEN, with no request bytes, for at most 1.5 s (never more than the handshake budget, half the operation timeout or half the peer idle timeout) and at most 8 per device, 64 per tenant and 256 per relay, then admits it on the committed carrier, or on the old carrier after a completed abort. The consumer sees an ordinary response, a little later. Only a freeze that outlasts the hold, or a full hold, reaches the consumer, and it does so as its own answer:

```
503 Service Unavailable
Retry-After: 1
{"code":"ROTATION_FREEZE","execution":"not_dispatched","message":"device data rotation is in progress; retry after the bounded hint","retryable":true,"retry_after_ms":250}
```

Nothing was dispatched, so a consumer or gateway may resend it after the hint. The owner-not-ready fault states keep their body unchanged: `503 PEER_UNAVAILABLE`, `not_dispatched`, `"selected owner is not ready; retry after the bounded hint"`, `retry_after_ms` 250. A consumer should not treat that body as a scheduled rotation, because the owner cannot say from it what an earlier request is doing. Across a cluster the owner makes the hold decision and signals a bound refusal to the ingress with the peer admission marker `rotation_freeze` (beside `owner_not_ready` and `capacity`), so a forwarded request's consumer sees the same `ROTATION_FREEZE` body as a local one. The ingress's peer fault diagnostics record it as cause `rotation_freeze`. An ingress older than this change does not know the marker and answers `503 PEER_UNAVAILABLE` `unknown` for it, so every relay in a cluster must run the same version, and with the same operation and peer idle timeouts ([cluster.md](cluster.md#scheduled-data-rotation-and-the-admission-hold)). The filesystem WebSocket upgrade and the finite unary echo are held the same way. The filesystem endpoint answers a freeze past the bound with `503 ROTATION_FREEZE` in its own error body ([filesystem-api.md](filesystem-api.md)), and the unary echo route with the body above.

Drain acknowledges transport receipt/accounting, not whole-response completion, so a long-lived SSE response cannot indefinitely pin the old socket. Control acknowledgments remain responsive during stalls; inability to drain within the overlap budget follows the protocol's explicit abort/recovery/failure path.

Recoverable loss with retained outer sequence/parser state replays only missing bounded transport bytes, deduplicated before this codec. An owner/process loss that destroys that state terminates the exchange. Do not reconstruct it by starting HTTP again, issue a second HEAD to a new handler, or infer resume from Content-Length. This transport has no ACP Last-Event-ID mechanism and cannot strengthen ACP/MCP recovery guarantees.

### Pinned in code (gate 1)

`crates/tunnel-http-forward` resolves the following points that the prose above leaves open. Each is peer-observable, so changing one is a protocol change.

- **Record payload limits.** A HEAD payload is 1–16,384 bytes; an empty HEAD is rejected. A BODY payload is 1–65,528 bytes. An END payload is exactly zero bytes.
- **Forbidden headers → `HTTP_INVALID_HEAD`.** These are rejected in both directions, and no policy can allow them: `host`, `connection`, `keep-alive`, `proxy-connection`, `content-length`, `authorization`, `proxy-authorization`, `proxy-authenticate`, `cookie`, `set-cookie`, and the `x-agent-tunnel-*` prefix.
- **Forwarded identity headers.** These are forbidden in the same way. The enumerated set is `forwarded`, `via`, `x-real-ip`, `x-client-ip`, `true-client-ip`, `cf-connecting-ip`, and the `x-forwarded-*` prefix.
- **Unsupported headers → `HTTP_UNSUPPORTED_FEATURE`.** These are also rejected unconditionally and cannot be allowed: `transfer-encoding`, `te`, `trailer`, `upgrade`, and `expect`. A consumer HTTP version that the selected policy does not accept also maps to `HTTP_UNSUPPORTED_FEATURE`.
- **Header values.** The codec rejects a value with leading or trailing space or tab; it does not trim. Ingress trims boundary optional whitespace once, as required above, before it encodes the head.
- **Header ordering.** The 32-field count is checked first. Then, per field in order: the name (lowercase token characters), the value (printable ASCII or tab), the running 8 KiB total, the forbidden and unsupported classification, the allowlist lookup, and the singleton repeat check.
- **Query alphabet.** Raw query bytes are RFC 3986 query characters, excluding `+` (form-decoding ambiguity) and `;` (legacy separator ambiguity).
- **Query pairs.** Pairs are split on `&`, and an empty pair is rejected. Only the first `=` separates key from value. A later `=` is value data, so base64 padding such as `cursor=YWJjZA==` is accepted.
- **Query keys.** Keys must be literal: a percent-encoded key is rejected even if it decodes to an allowed name. The decoded key is compared ASCII-case-insensitively against a credential list that no policy can allow: `access_token`, `id_token`, `refresh_token`, `token`, `api_key`, `apikey`, `api-key`, `key`, `password`, `passwd`, `secret`, `client_secret`, `auth`, `authorization`, `session_token`, `x-amz-security-token`, `x-amz-signature`, `sig`, and `signature`.
- **Query values.** Values are percent-decoded exactly once for the policy decision. The result must be valid UTF-8 with no Unicode control characters. The original query bytes are what is forwarded.
- **Paths.** A trailing slash (`/acp/`) is rejected as an empty segment. `/` alone passes syntax but must still match an advertised route.
- **Status.** `status` must be a JSON integer lexeme of exactly three digits in 200–599. Fractions and exponents are rejected, so `200.0` and `2e2` are invalid even though they equal 200.
- **Grammar errors.** An END or BODY record before HEAD is a protocol error (`HTTP_BAD_RECORD`), decided from the fixed header alone. Any byte after END fails on arrival and is classified by its kind byte, so the error does not depend on how the stream was split.
- **Per-record progress budget.** When a partly received record misses its completion budget, the caller reports `HTTP_DEADLINE_EXCEEDED`. That code is shared with the absolute application deadline. The codec is clock-free: the caller supplies progress-clock observations and pauses its clock during a freeze or withheld credit.
- **Body limit ceiling.** A configured cumulative body limit is finite and at most 1 TiB (2^40 bytes). A policy above the ceiling cannot be constructed, so no unlimited sentinel exists.

The implementation PR pins codec fixtures, all limits, per-profile header/path allowlists, HTTP library features, and the supported errors in code. Keep this codec independent of Axum extractors, ACP JSON-RPC types, and child supervision so its behavior can be reasoned about and tested without a running server.

### Pinned in code (gate 2)

`crates/tunnel-http-bridge` connects the codec to `http::Request`/`http::Response` values with streaming `http-body` bodies. The owner adapter is `forward`; the device adapter is `serve`, which takes frame queues and a handler and no address. It depends only on crates already in `Cargo.lock` and does not enable Tokio's `net` feature. It resolves these points beyond the prose above.

- **Stream stand-in.** Gate 2 runs over a bounded in-process queue per direction, not the tunnel. DATA is charged byte-for-byte against credit that is released only when the receiver takes it. FIN and RESET are ordered behind earlier DATA but use reserved slots, so exhausted credit never blocks them. Any RESET also raises an out-of-band signal, standing in for control `CANCEL`, so a receiver stalled on its own downstream stops promptly, including when the RESET is queued behind the sender's FIN (for example, a consumer that disconnects after its upload finished while the handler has not read it). The signal records whether FIN preceded the RESET. The device's request pump acts on any RESET: a RESET the owner queues after its request FIN can only mean the consumer or its deadline went away, and the request direction is only upload bytes the handler has not consumed, so no completed direction is lost. The owner's response pump, while delivering a response, acts only on a RESET sent before the device's FIN, so a later RESET never truncates a response the device completed. The RESET carries `code` and `execution` in place of the protocol reason code plus `RESULT_STATUS`. Mapping these to the numeric reason-code registry is gate-3 work.
- **Ingress consumes only transport fields.** The owner consumes `host`. For HTTP/1.1 it consumes `keep-alive`, and `connection` only when every option is `keep-alive` or `close`; any other option, including one that nominates a field, is `HTTP_UNSUPPORTED_FEATURE`. In an HTTP/2 request `connection`, `keep-alive` and `proxy-connection` make the request malformed (RFC 9113 section 8.2.2) and are `HTTP_INVALID_HEAD`. It consumes `expect: 100-continue`; any other expectation is `HTTP_UNSUPPORTED_FEATURE` with status 417. It consumes one HTTP/1.1 `transfer-encoding: chunked` without Content-Length, because the HTTP library has already decoded it. It consumes `content-length` into `body_length`. A URI scheme and authority are not forwarded. Every other field goes to the codec allowlist, so credentials such as `authorization` and `cookie` fail rather than being stripped: the gate-3 ingress must remove them after it verifies them.
- **Content-Length.** Exactly one field whose trimmed value is `1*DIGIT` (leading zeros are accepted, comma lists are not) becomes `body_length`. Two fields are `HTTP_INVALID_HEAD` even when equal, and so is Transfer-Encoding with Content-Length. Other transfer codings, and any transfer coding in HTTP/2 or in a handler response, are `HTTP_UNSUPPORTED_FEATURE`. A declared length above the direction's limit fails before dispatch with `HTTP_BODY_LIMIT`. The sending pump fails as soon as its bytes exceed the declared length, and at the end if they fall short. It never puts more BODY bytes on the wire than it declared.
- **Trailers and encodings.** A `trailer` field is `HTTP_UNSUPPORTED_FEATURE` before the codec runs. A non-empty trailer frame discovered while pumping resets the exchange with the same code; an empty trailer map is ignored. A `content-encoding` value other than `identity` (ASCII case-insensitive, per field line) is unsupported; `identity` is forwarded only when the profile allowlists the field.
- **Handler responses.** Only `content-length` is consumed, and it must equal the body's exact size hint when both exist. For HEAD and 304 a handler Content-Length is a representation-size hint: it is dropped, not forwarded and not checked against the body. For 204 and 205 only `0` is accepted; a non-zero value is `HTTP_LENGTH_MISMATCH`. None of these responses may have a known non-zero size, and the body is drained before the head is sent, so any data is a clean pre-header `HTTP_LENGTH_MISMATCH` rather than a truncated stream. The owner generates Content-Length from a checked `body_length`, except for these zero-body responses.
- **Gateway statuses.** Before response headers commit, a failure caused by the consumer's request maps `HTTP_BODY_LIMIT` to 413, an unsupported `expect` to 417 (RFC 9110 section 15.5.18), any other `HTTP_UNSUPPORTED_FEATURE` to 501, and any other code to 400. An upstream failure maps `HTTP_DEADLINE_EXCEEDED` to 504, `HTTP_STREAM_INTERRUPTED` with `not_dispatched` to 503, and anything else to 502. The body is exactly `{"error":{"code":"…","execution":"…"}}` with `cache-control: no-store`, and the same pair is attached as a typed response extension. One addition, at the public ingress only (M6-C58): when the codec refuses the request head because of a header the selected profile does not allowlist, the relay's body also carries `"header":"<name>"`, the first such header's lowercase name (never its value), so a consumer is told what to remove. Before the codec runs, the ingress drops `user-agent`, `accept-encoding`, `accept-language` and `sec-fetch-mode` unless the profile allowlists them, alongside the verified `authorization` and `cookie`; see [mcp.md](mcp.md).
- **Execution knowledge.** The owner reports `not_dispatched` until the REQUEST_HEAD record is wholly queued, then `unknown`. A head larger than the stream credit could be partly queued before a failure, so it is `unknown` from the start. It reports `dispatched` once a RESPONSE_HEAD arrives, because the device only sends one after the handler returns. It adopts the device's `execution` from a device RESET. The device records `dispatched` when it starts the handler task. That decision and the first-failure record share one lock, so a RESET never claims `not_dispatched` for a handler that starts afterwards. On cancellation the device waits for the aborted handler future to be dropped before it reports. A handler future can therefore be dropped without ever observing its body fail; only its synchronous `Drop` cleanup is guaranteed to run. Work that must outlive the handler belongs in a separate task that watches the request's `HandlerCancellation`.
- **END is not success.** A decoded body ends successfully only after the direction's FIN. END followed by RESET or carrier loss is an error on the body, never a clean end. Chunks already queued in order before a failure are delivered before the error; the queue is bounded to four chunks.
- **Terminal discard.** After a local failure, an endpoint keeps receiving and discarding peer frames until the peer's own FIN, RESET or carrier loss, so the peer learns of the RESET in order rather than seeing a vanished receiver. The discard is bounded by the exchange deadline plus a grace of `min(deadline, 5 s)` (`DISCARD_GRACE`), so a peer that never finishes cannot hold the exchange open, while a deadline abort still lets the peer see the RESET and record `HTTP_DEADLINE_EXCEEDED` rather than an interrupted carrier.
- **Early responses and uploads.** If the handler drops its request body, the device keeps validating the remaining upload records and discards the bytes. After the response completes, the owner keeps forwarding the upload. A later upload failure resets the stream, but the completed response stays complete in both endpoints' reports.
- **Backpressure bounds.** Each pump holds at most one local body frame and polls the next only after the previous one fits outbound credit. Decoded bodies queue at most `BridgeConfig::body_queue()` chunks (default 4, ceiling 64). Tests assert the handler cannot produce, and the ingress cannot read, more than one chunk plus credit, one DATA frame and the body queue while the other side is stalled.
- **Diagnostics.** `Debug` for stream frames, bodies and normalized heads prints lengths, counts, method, version and status only; never body bytes, header values, paths or query text.
- **Header order.** `http::HeaderMap` preserves the order of values within one name but not the interleaving across names. The head therefore lists each name's values together.
- **Not yet pinned.** The device dispatches after a validated head and streams the request body; the ACP/MCP/CUA buffer-before-dispatch rule and enumerated per-profile allowlists are gate-5 work (the test profile is a fixture only). `BridgeConfig::deadline()` is the absolute application deadline: it is always finite (default 300 seconds), and a value of zero or above the 24-hour ceiling cannot be configured. The per-record, first-HEAD and FIN progress budgets (`RecordDeadline`) are not wired into the pumps yet.

### Pinned in code (gate 3)

Gate 3 puts the gate-2 `forward`/`serve` behind the real path: consumer → public Axum route → (non-owner ingress: credited peer HTTP/3 hop →) owner actor stream → device data WebSocket → `tunnel-client` → in-process handler. `forward` and `serve` are unchanged; each real hop is a carrier behind a trait. These choices are peer-observable unless marked local.

- **Carriers and handoffs.** A carrier implements `CarrierWriter` (`data`, `finish`, `reset`) and `CarrierReader` (`next`, plus an out-of-band `reset_signal`). `pump_outbound`/`pump_inbound` move frames between the carrier and the gate-2 channel, which becomes a *handoff* of `HANDOFF_CAPACITY` = 65,536 bytes (one DATA frame); a pump holds at most one frame outside it. A RESET the bridge raises before its FIN preempts an outstanding DATA write (exhausted carrier credit never delays it); a RESET after FIN is written in order, so a completed direction is never truncated; a direction the bridge drops before FIN is reset (`HTTP_STREAM_INTERRUPTED`, `unknown`), never finished. Inbound, a pump waiting on handoff credit reads at most one further event ahead and watches the carrier's signal: a peer RESET before the peer's FIN resets the bridge at once; one after FIN only raises the bridge's signal while the ordered DATA, FIN and RESET are still delivered. Carrier readers are cancel-safe: an outstanding read survives a dropped `next` future.
- **RESET reason registry.** `tunnel_protocol::reset_reason`: 4001 `AUTHORIZATION_EXPIRED`, 4002 `PROTOCOL`, 4003 `RECORD_LIMIT` (the three codes already in use), and new 4004 `ADAPTER_FAILURE` and 4005 `CANCELLED`. A bridge failure maps `HTTP_CANCELLED` to 4005 and every other `HTTP_*` code to 4004. There is no private numeric extension; a receiver rejects an unregistered code on the peer hop.
- **RESULT_STATUS.** A new control message `RESULT_STATUS {message_id, session_id, epoch, stream_id, operation_id, outcome, detail?}`. `outcome` is one of `succeeded`, `failed`, `cancelled`, `outcome_unknown`; `detail` is `{code, execution}`, each 1–64 bytes of `[A-Za-z0-9_]`, at most 512 serialized bytes; unknown fields are rejected. A connector that resets an HTTP stream sends `RESULT_STATUS` (`cancelled` for `HTTP_CANCELLED`, `outcome_unknown` for `unknown` execution, otherwise `failed`) on the control socket before it queues the RESET on the data socket. The owner correlates it by stream and operation identity and ignores it for a forgotten or non-HTTP stream. Because the two sockets are unordered, a reader that receives the RESET first waits at most 500 ms (local) for the status, then infers `{HTTP_CANCELLED or HTTP_STREAM_INTERRUPTED, unknown}` from the reason alone. The owner never sends `RESULT_STATUS` to a connector, and a connector rejects an unsolicited one as a protocol error.
- **Service, grant and OPEN.** The catalog service type is `http-forward`; the grant operation and consumer token scope are `http:invoke`. Every path resolves the service through the shared resolver restricted to that type, so an echo service is never reachable through the HTTP route or the reverse. OPEN uses operation `http_forward` with 131,072-byte initial windows in both directions. A connector admits it only for an export configured with `type = "http-forward"` *and* an in-process handler registered through `tunnel_client::connect_with_http_handlers`; otherwise it answers `OPERATION_DENIED`. The M1 profile never admits it.
- **Public route.** `ANY /v1/devices/{device}/services/{service}/http/{*path}` on the consumer listener. A relay serves it only when started with an `HttpForwardExport` (profile plus `BridgeConfig`); every production caller passes none, so it answers 404 until gate 5. Order: cluster readiness, relay-global admission, bearer verification for `http:invoke`, device and typed service resolution, grant check, per-owner-scope admission. Only then are `authorization` and `cookie` removed: the bearer was verified; a cookie is never an accepted credential in the token profile (docs/cluster.md defers browser sessions), so it is removed without being honored. Every other credential, forwarded-identity or `x-agent-tunnel-*` field is left for the codec to reject (400). The export path is the *undecoded* request target after `/http`, with the original query; `/http` itself is not routed. The exchange deadline is the smaller of the export deadline and the verified token's remaining lifetime.
- **Peer hop.** A non-owner ingress opens the existing `POST /internal/v1/streams` exchange with `required_scope = http:invoke`; the raw bearer travels only in that authenticated envelope. The owner re-authenticates it, re-resolves the typed service and re-authorizes the grant before admitting the stream. Each `ConsumerChunk` body starts with a tag: `1` DATA (1–65,535 payload bytes), `2` FIN, `3` RESET (reason `u16` BE, `HTTP_*` code index, execution index; the reason must be registered and equal the code's mapping), `4` CREDIT (cumulative consumed encoded bytes and records, `u64` BE each). Each direction has its own window of `PEER_HOP_WINDOW_BYTES` = 196,608 encoded bytes (9 + payload per DATA record, within the 256 KiB per-stream peer budget) and `PEER_HOP_WINDOW_RECORDS` = 64 records. A sender writes DATA only within the window; the receiver reads continuously (so CREDIT and RESET are never stuck behind an unread body), counts a DATA record as consumed when it leaves its queue for the next hop, and closes the hop on a window violation. A writer still accepts RESET after its FIN, and finishes its HTTP/3 send only after its own and the peer's terminal.
- **Owner relay.** The owner relays the peer hop and its actor stream through two handoffs and remains the only authority for tunnel sequences and credit. It does not re-parse `http-forward/1` records; the ingress and the device both validate against their profile (see below).
- **Owner actor stream.** DATA carries raw record bytes. A write completes when its chunk is sequenced; it parks, charged to the session budget, while send credit or replay capacity is insufficient (an HTTP stream's replay and reorder limits cover its whole window) and is retried on WINDOW_UPDATE or ACK. Received DATA waits in a per-stream buffer, charged to the session budget and bounded by the advertised window, and WINDOW_UPDATE is issued only when the reader takes a chunk, never on receipt. A connector FIN half-closes only the response direction (no FIN reply). A connector RESET is mirrored as before and also published out of band with whether it followed the connector's FIN. Closing a stream sends FIN only if both directions already finished; otherwise it sends `RESET(CANCELLED)`, which may follow the owner's own FIN.
- **Connector stream.** The same discipline: request bytes release receive credit only when the handler side reads them; the request FIN half-closes only the request direction, and the connector sends its FIN only when the handler's response completes; a write parks (including while writes are frozen for rotation) instead of failing the session; an HTTP stream's RESET may follow its FIN; authorization refresh challenges run for HTTP streams exactly as for `echo_stream`, and each read re-checks the authorization and operation deadlines; the operation deadline is `limits.operation_timeout_ms`.
- **Diagnostics (local).** `RelaySnapshot.http_forward` keeps at most 64 owner-stream records (receive buffer, parked and replay high-water, release `fin`/`reset`/`closed` and reason) and 64 exchange records per role (`ingress_local`, `ingress_remote`, `owner_peer`: handoff, response-body and peer-hop high-water marks and terminal labels). `HttpHandlers::diagnostics()` keeps 64 device records (receive buffer, parked, handoffs, request body and the device `ExchangeReport`). All are identifiers, byte counts and closed labels only.
- **Measured bounds (`verify-m3-http-forward-real-path`).** With one 16 MiB echo saturated in both directions, every run observed: handoffs ≤ 65,536; ingress response body ≤ 4 × 65,528; peer in-flight and receive queues ≤ 196,608; owner and device receive buffers ≤ 131,072; parked writes ≤ 65,528; owner replay ≤ 131,072; the owner session data high-water under its data limit. The gate also requires each saturated hop to have exceeded half its window, so the bounds are not met vacuously.
- **Not proven by gate 3.** Rotation, freeze, recovery and progress budgets on HTTP streams (addressed by gate 4 for scheduled rotation, below; recovery replay of a partly received record is still not exercised). Owner re-validation of `http-forward/1` records (added in gate 4). A control `CANCEL` for an HTTP stream (added in gate 4, sent only while a RESET is deferred behind a freeze). Still open: no scoped operation-status lookup exists; `RESULT_STATUS` correlation is bounded by a timing grace, not ordered; only HTTP/1.1 consumers are exercised; per-profile allowlists and buffer-before-dispatch profiles remain gate 5.

### Pinned in code (gate 4)

Gate 4 runs the gate-3 path through scheduled rotations and faults, and closes gate-3 review findings A–F. Items are local unless marked peer-observable.

- **Progress budgets (finding A).** `tunnel_http_bridge::ProgressBudgets` holds first HEAD (10 s), record completion (10 s), credit stall (30 s) and FIN after END (10 s), each finite and at most `MAX_PROGRESS_BUDGET` = 600 s. `serve_paused` (device) arms first HEAD, record and FIN-after-END clocks on its request pump; `forward_paused` (ingress) arms record and FIN-after-END clocks on its response pump; every carrier write arms the credit-stall clock, which restarts after each completed send. A clock counts only time spent waiting on the carrier: it stops while the endpoint's `PauseSignal` reports a rotation freeze, and time blocked on its own downstream (withheld credit) is not measured. Trickled bytes of one record do not restart the record clock. An expiry fails the exchange with `HTTP_DEADLINE_EXCEEDED` and is reported as `progress_expired` (`first_head`, `record`, `credit_stall`, `fin_after_end`) in `ExchangeReport` and in the relay and device diagnostics. The owner relay itself arms no progress budget; it is bounded by the exchange deadline and by the budgets of the two endpoints around it.
- **Freeze signals.** The owner actor publishes each HTTP stream's writer freeze to its exchange task. It does this after a command only for the session that command names (every data frame, control message and HTTP stream command names one; ticks and registrations consider every session), and it visits that session's streams only when the session's freeze state actually changed since the last publication. The connector actor publishes after every loop iteration. **Peer-observable:** the peer hop gains record tag `5` PAUSE (one byte, `1` frozen, `0` thawed). The owner relays its freeze over the hop, and the remote ingress's clocks pause for exactly that freeze. A PAUSE carries no credit and is not a DATA record.
- **Deployment caveat: PAUSE has no version negotiation.** The hop carries no feature or version exchange. A peer built before gate 4 treats tag `5` as an unknown record and closes the hop, so during a mixed-version rollout any HTTP exchange crossing an old and a new relay is interrupted (`HTTP_STREAM_INTERRUPTED`). Roll all relays of a deployment together, or keep HTTP exports disabled until every relay serves gate 4.
- **Owner re-validation (finding B).** The owner relay parses both directions with its own copy of the export profile (`RequestReader`, and `ResponseReader` keyed by the validated request method) before it forwards a chunk. A violation forwards nothing more, resets both directions and records the error on the `owner_peer` exchange record. A request head rejected at the owner was never forwarded, so it reports `not_dispatched`. A forged `x-agent-tunnel-*` head injected past the ingress is rejected with nothing forwarded.
- **Pure state helpers (finding C).** `HttpStreamState` (owner) and `DeviceHttpState` (connector) expose their read, park, credit, terminal, freeze and cancel decisions as pure functions with unit tests. The rotation gate is not their only evidence.
- **Aggregate hop bound (finding D).** Every HTTP hop to one peer shares a per-direction aggregate of `HOP_AGGREGATE_BYTES` = `CONNECTION_BYTE_BUDGET / 2` encoded bytes (4 MiB), keyed by peer node identity. A sender waits for aggregate room after it has hop credit; a receiver closes a stream whose peer exceeds the aggregate. Charges are released on consumption, on CREDIT and when a hop is dropped. A unit test drives 40 saturated fake hops and asserts the peak stays within the bound, with a control run that exceeds it without the aggregate. The aggregate is not the peer `ConnectionBudget`: that counter charges each record per physical connection (and per stream) only while the record is being received or sent, and a hop releases the reservation as soon as it decodes the record. The aggregate covers what happens after that early release, the hop bytes that are queued for the next hop or in flight awaiting CREDIT. It is keyed by peer node (so several connections to one node share it) and is independent of the per-connection reservation counter. The 8 MiB peer-connection ceiling in [cluster.md](cluster.md) is therefore not enforced as one number: the transient maximum for one peer is 4 MiB of aggregate hop bytes per direction plus whatever records the per-connection reservation counter holds at that instant (itself at most 8 MiB per connection).
- **Ingress validation before admission (finding E).** The public route runs `normalize::request_head` against the export profile directly after verification and credential removal, before owner routing, peer streams or tunnel streams. A rejected head is answered 400/413/417/501 and counted in `ingress_rejected_before_admission`. The gate proves that counter rises by one while ingress exchanges, owner streams, owner exchanges and handler invocations do not change.
- **Control CANCEL (finding F).** A local `RESET(CANCELLED)` that is not on the wire yet gets a scoped control `CANCEL` too, provided the device has neither finished nor reset its direction. This covers two cases:
  - The RESET is deferred behind the freeze (unsequenced, `reset_deferred_by_freeze`).
  - The data writer queue refused the RESET outside a freeze. The RESET is then kept as the stream's pending terminal and retried in order on every 500 ms actor tick while the terminal-failure deadline runs, and sooner on an ACK that releases a parked HTTP chunk or a WINDOW_UPDATE that releases parked stream writes. If the deadline expires first, the session closes with `TERMINAL_FIN_TIMEOUT`.

  The connector's `handle_cancel` stops the HTTP exchange out of band at once. The bridge then emits the stream's own ordered `RESET(CANCELLED)` and `RESULT_STATUS`. The connector emits the RESET itself only for an exchange that already ended and is not settled (below). A CANCEL refused by the bounded control queue is recorded where it was refused, and the session is closed with `CANCEL_UNDELIVERABLE` after the command. When the RESET was queued normally, no CANCEL is sent, because the ordered RESET is not delayed.
- **Full writer queue (M6-C190, M6-C191).** A raw HTTP (or `fs_9p`) chunk the relay's bounded data writer queue refuses only because it is momentarily full is backpressure, not a failure. The chunk parks at the head of the stream's bounded FIFO, charged to the same per-stream and session budgets as a credit-held record; a later chunk and the owner's FIN wait behind it. Nothing is sequenced for it until then, so there is no sequence gap and nothing to replay. A record parked before the owner's FIN (for credit, replay room or the writer) is still sequenced ahead of that FIN.
  - **Retry.** Parked streams are tracked per session. After every actor command and on the 500 ms tick, a session whose writer has no free slot, or which still owes ACKs, is skipped with one comparison; otherwise its owed ACKs are retried first (they are flow control, and the session is fenced if the carrier takes none of them for 5 s), then its parked streams in stream-ID order, each head record checked against the writer's free slots before it is popped. A WINDOW_UPDATE or ACK that retries a stream's held records makes the same check. A retry against a still-full writer therefore copies and encodes nothing.
  - **Bound.** A drained writer is noticed at the next command or within 500 ms. New writes run before the retry and can take freed slots first, so a parked chunk has no priority over them. How long a chunk can stay parked is bounded by the device's own budgets (10 s first HEAD or record, 30 s operation deadline), after which the device resets the stream; by a consumer or relay RESET, which discards the parked records; and by the session's writer fences (a writer that takes none of the owed ACKs or terminal frames for their 5 s window closes the session).
  - **Counters.** `tunnel_relay_http_writer_parks_total` counts each parked chunk once; `tunnel_relay_http_writer_reparks_total` counts retries that popped a parked chunk and had to park it again (expected to stay at zero).
  - **A write the owner actor still refuses** (a closed carrier, an exhausted budget, a stream that is gone) makes an `http-forward/1` actor carrier reset the stream before it reports the carrier closed, so the device stops at once and the consumer is answered promptly with an explicit `HTTP_STREAM_INTERRUPTED` (execution `unknown` once any of the request may have reached the device); nothing is retried. A filesystem (`fs_9p`) carrier does not reset: its consumer close code is the device's RESET reason (`AUTHORIZATION_EXPIRED` is 1008) or the grant timer, and a relay RESET would end its reader with no code first.
  - Before M6-C190, the refusal ended the ingress's outbound pump without a RESET, and the device held the truncated request until its 10 s first-HEAD or record budget, or its 30 s operation deadline, which the consumer saw as `HTTP_DEADLINE_EXCEEDED` after 10 -- 30 s, some of them `dispatched` (M6-C181; [soak-2026-09-27.md](soak-2026-09-27.md)).
- **Failed-exchange diagnostics (M6-C190).** With `AGENT_TUNNEL_HTTP_EXCHANGE_LOG=1` (off by default; a routine consumer cancel releases a stream without both FINs, so the lines would otherwise scale with ordinary traffic), the relay logs one `warn` line per failed ingress exchange (`http_forward_exchange_failed`, the payload-free exchange record), how each carrier pump ended (`http_forward_exchange_pumps`), each refused actor write's closed code (`http_forward_actor_write_refused`), and each owner HTTP stream released without both FINs (`http_forward_owner_stream_unfinished`: the owner-stream record plus its age, authorization challenge counts, parked chunks, send credit and owed credit), and the connector writes one `http-exchange-failed` JSON line per failed exchange to stderr: the exchange report, request record counts, authorization state, send credit, replay use and parked bytes. All carry identifiers, counters, flags and elapsed milliseconds only. `scripts/m6-soak.py` sets the variable for both processes and extracts exactly these lines into `http-failures.jsonl`, the only log-derived file its artifact carries.
- **Owner stream records.** Owner-stream diagnostics carry request and response record positions, the owner's RESET sequence and carrier generation, `reset_deferred_by_freeze` and `cancel_sent`. A stream whose terminal is still deferred is recorded when it is reclaimed, so the record shows the sequence and carrier the terminal actually used; a session that ends first records every unrecorded HTTP stream once at teardown. Each published `STREAM_FORGET` is recorded (at most 64 retained).
- **Rotation observations.** At QUIESCE the owner captures each HTTP stream's sequenced request position, received response position, parked and receive-buffered bytes, deferred terminal and `last_emitted`. At the attempt's COMMIT decision, while the roster is still frozen, it records these with the relay and connector fences and acknowledgement cursors as `HttpRotationObservation` (64 retained). Recording at commit rather than at completion keeps streams that are forgotten right after activation.
- **Settled exchanges emit no RESET after FIN.** A connector HTTP stream is *settled* when its response FIN is sequenced, or already retained for the carrier behind a writer freeze or a full queue, and its request FIN was received in order. A settled stream skips authorization refresh and expiry. An owner `CANCEL` for it stops nothing further and queues no RESET. Without this, an expiry or a CANCEL could emit a RESET after FIN while the owner, having seen both FINs, was already publishing `STREAM_FORGET`. The owner never acknowledged that RESET, and the connector closed the session on "STREAM_FORGET terminal proof did not converge".
- **Declared-length public bodies.** Dropping an ingress response body after the reader took every octet of a declared `Content-Length` is not a cancellation. HTTP servers stop polling at the declared length, before END and FIN arrive. The exchange then completes on its own END and FIN, which the owner's response pump bounds: it arms the FIN-after-END budget at the last declared byte, so a device that never sends END and FIN fails the exchange with `fin_after_end` instead of holding it to the absolute deadline.
- **Fixture hold (test only).** `HttpForwardExport::fixture_hold` (`HttpRelayHold`, doc-hidden) stops the owner relay's next actor write once, at a named point: inside a BODY record header after N bytes, inside a BODY payload, or before the request FIN. It releases itself after `HOLD_CEILING` = 30 s. The ingress writes records back to back, so these positions are otherwise reachable only by timing. An `HttpRelayHold` can be constructed only with the `tunnel-relay` cargo feature `test-fixtures`, which `tunnel-test-harness` enables. A relay built without the feature refuses to start with a hold and never honours one. Cargo unifies features across one workspace build, so `cargo build --workspace` still compiles the relay binary with the feature; a production relay must be built on its own (`-p tunnel-relay`). An unarmed hold is a pass-through.
  - **Superseded in gate 5 (2026-09-16).** The `test-fixtures` feature is gone.
    - `tunnel-relay` now defines only the doc-hidden `HttpRelayInterposer` hook and the `HttpRelayHoldPoint` vocabulary.
    - `HttpRelayHold` and `HOLD_CEILING` live in `tunnel-test-harness` (`http_relay_hold`), attached through `HttpForwardExports::with_fixture_interposer`.
    - `serve` builds its exports only from `ServeConfig`, which cannot express an interposer. No relay artifact, workspace-built or not, contains a hold implementation.
    - Relay unit tests assert that configured exports carry no interposer and that the manifest has no `test-fixtures` feature.
- **Membership refresh interrupts peer hops (observed, not changed).** A newer signed membership record version invalidates every peer admission bound to the old version, and with it every in-flight peer HTTP hop (seen as `HTTP_STREAM_INTERRUPTED` at ingress and `RESET(CANCELLED)` at the owner). A long-lived SSE response through a non-owner ingress therefore does not survive a membership re-sign. The gate re-signs the fixture's 60-second records only at case boundaries, at most every 15 s, and waits for both ingress routes to answer `/ping` again. Re-signs in quick succession can leave every relay's peer readiness down (`CLUSTER_UNREADY`) with every readiness probe failing on a remote-closed HTTP/3 connection. Both are recorded as defects in [tasks.md](tasks.md) (M7-C80 and M7-C81) and in [cluster.md](cluster.md)'s interruption table.
- **Measured (`verify-m3-http-forward-rotation`).** The gate uses the three-relay production cluster: the owner is relay-a, the ingress is relay-c, and the rotation policy is `{interval 6 s, handshake 2 s, overlap 5 s}` with record, credit-stall and FIN-after-END budgets of 60 s, above its 44 s observation bound. Each case is observed at its own rotation: HEAD only (`boundary`); inside a BODY header (`partial_header`, 3 bytes); inside a BODY payload (`partial_body`); END sequenced before FIN; an early response during upload; a credit-stalled 6 MiB download with the owner receive buffer above half its window; and SSE across two rotations with events split inside UTF-8 and delimiters. Every case passes these checks:
  - the relay fence equals the frozen `last_emitted`;
  - both acknowledgement cursors reach their fences;
  - the new generation is newer;
  - one handler invocation, one device HEAD and one END with FIN;
  - status 200 with a SHA-256-exact or byte-exact body ending cleanly;
  - no device or ingress error or progress expiry;
  - an eventual `STREAM_FORGET`.

  The cancel race holds a freeze by pausing the active data socket's connector→relay bytes after one more response chunk is sequenced. It then disconnects the consumer and checks:
  - the handler's cancellation is observed while the owner stays frozen;
  - the owner defers an unsequenced RESET and sends `CANCEL`, and the device records `cancel_received`;
  - the owner RESET is sequence `fence + 1` on the new generation (4 after fence 3, generation 2);
  - device and ingress both record `HTTP_CANCELLED`, and the stream is forgotten.

  With relay-a↔relay-b blackholed after a synthetic side effect entered through relay-b, and with relay-a shut down after one entered through relay-c, each fault checks:
  - the handler ran exactly once before the fault and was not run again;
  - the consumer sees 502 `HTTP_STREAM_INTERRUPTED` with `execution: unknown`;
  - that code and execution map to `outcome_unknown` through the same rule the connector uses for `RESULT_STATUS`;
  - the ingress exchange record shows `unknown` execution.

  Every settled steady state had two device sockets (control plus one data socket); the peak was 3, during a candidate. The gate completed 9 rotations.
- **Red-then-green.** Each guard was temporarily removed, the evidence re-run, and the guard restored:
  - Not queuing the owner's `CANCEL` fails the gate: the handler is never cancelled during the freeze, and the held attempt expires into recovery.
  - Removing the early ingress normalization fails "forbidden head refused before admission": `rejected_before_admission_delta` is 0 and an ingress exchange opens.
  - Disabling owner re-validation fails the forged-head and grammar owner-relay tests.
  - Treating a stream as settled without its response FIN fails the connector authorization unit test.
  - The aggregate test carries its own control run.
- **Not proven by gate 4.**
  - A scoped operation-status lookup: the `outcome_unknown` verdict comes from the ingress record and gateway body, not from a lookup.
  - Ordered `RESULT_STATUS` correlation: it is still bounded by the 500 ms grace.
  - Rotation *recovery* replay of a partly received HTTP record, and forced retirement.
  - Progress budgets on the owner relay, and an expiry on the real path (the unit tests cover all four kinds).
  - HTTP/2 consumers.
  - A long-lived exchange spanning a membership refresh through a non-owner ingress (it is interrupted, above).
  - "No retry" beyond the moment of the outcome. The handler counter is read when the consumer receives its 502; a retry issued later, for example after a successor owner claims the device, would not be observed.
  - Per-profile allowlists and buffer-before-dispatch profiles, which remain gate 5.

### Pinned in code (gate 5, MCP)

Gate 5 for MCP is recorded in [mcp.md](mcp.md#pinned-in-code-m3-01-and-m3-02). The points that change this contract are:

- **Header prefix rules.** `HeaderPolicy::allow_prefix` admits a name family such as `mcp-param-`. The occurrence applies per complete name, and the bare prefix is not a member. A prefix cannot cover, or be covered by, any forbidden or unsupported name or prefix.
- **Enumerated profiles.** The MCP request and response allowlists are enumerated per profile. Everything unlisted fails validation at the ingress, owner and device, as gates 1–4 already enforce.
- **Profile selection.** The relay serves a set of profiles (`HttpForwardExports`) from `ServeConfig [http_forward]`. Each public request and each owner peer stream selects its profile from its own authorized catalog read of the service capability `http_forward_profile`. Where none matches, the answer is 404 before normalization or any stream.
- **Capability changes in flight.** The ingress and the owner read the catalog separately. If the capability changes between the two reads, the owner may validate under a different profile, or under none, and refuse the stream. That failure is closed: an owner re-validation `HTTP_INVALID_HEAD`, or a refused stream, never a head forwarded under the wrong profile.
- **Buffer before dispatch.** For both MCP profiles the device collects the complete bounded body and validates it before invoking a backend. The relay still streams request bodies; only the device dispatch waits. A request rejected there never reaches the backend, and its local JSON-RPC error is an ordinary completed HTTP response.
- **Fixture hold.** The hold moved to the harness; see gate 4.
- **Proven over the real path.** `verify-m3-mcp-cloud-client` (M3-03) runs both MCP profiles over the real Axum → HTTP/3 → owner actor → device WebSocket path with relay profile selection from `[http_forward]` and the catalog capability, across scheduled rotations; see [mcp.md](mcp.md#pinned-in-code-m3-03).
- **Not proven.** Consumer isolation, concurrent correlation and unknown outcomes for MCP (M3-04). The CUA allowlist remains open.

### Pinned in code (gate 5, ACP)

`crates/tunnel-acp` adds the `acp-http-v1` profile: `POST`/`GET`/`DELETE` at `/acp`, **HTTP/2 only**, an empty query, the request headers `content-type`, `accept`, `acp-connection-id`, `acp-session-id` and `tunnel-principal-binding`, and the response headers `content-type`, `cache-control`, `x-accel-buffering` and `acp-connection-id` — every one a singleton, and no prefix rule. Buffer-before-dispatch applies as it does for MCP: the device validates one complete bounded JSON-RPC message before anything is invoked. The enumerated table and its refusals are in [acp.md](acp.md#pinned-in-code-m8-01); the artifacts it is pinned against are in [sources.md](sources.md#acp).

This is gate 5's **profile table only**. It has not been served: no relay serves `acp-http-v1`, no device export exists, and no ACP fixture has been run through the bridge. The codec passing its tests does not establish application compatibility, and neither does a profile table passing its own.
