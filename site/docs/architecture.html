DEVELOPMENT DOCUMENTATION / ARCHITECTURE

An outbound connection with scoped authority.

The relay connects a consumer to a specific enrolled device and service. Authorization and local export policy both constrain what can happen.

How it fits together

Three flows, one diagram: how the relays share a device, how the client daemon connects, and how an agent's request reaches a local capability. This describes the documented design. The cluster profile has local harness evidence only and its acceptance is still open.

1. How the relay cluster passes connections between servers

Several relays share one Redis. A device is owned by exactly one relay at a time, a request may arrive at any of them, and the relays forward to the owner over a private link.

  1. Several relays, one entry. The diagram shows three relays, the size the repository's cluster harness uses; signed membership allows up to 32. Any relay can accept a consumer request or a device socket.
  2. One authoritative store. A single Redis is the only shared store. It holds the catalog of grants, the device ownership leases and the signed membership records. It holds no payloads, sockets, private keys or replay buffers.
  3. Who is a relay. A separate membership authority signs the approved set of relay public keys. Redis only distributes those signed records; it is not a root of trust and never holds private keys.
  4. Private peer links. Relays talk to each other only over private HTTP/3 (QUIC) with mutual TLS, using relay identities that are distinct from device credentials. A device certificate cannot act as a peer.
  5. One relay owns the device. The device's control socket reaches Relay B, which claims the owner lease for that device in Redis with one atomic script. The lease lasts 30 seconds by default and is renewed every 10.
  6. A request arrives anywhere. A consumer request lands on Relay A; the load balancer needs no sticky routing. Relay A authenticates and authorizes the request, then looks up the device's owner in Redis.
  7. Forward once to the owner. Relay A forwards the exchange straight to Relay B over the private peer link. The hop budget is exactly one: a relay that is not the owner answers that the owner changed instead of forwarding onward. Applies when the request enters at a relay that does not own the device.
  8. No hop needed. Here the request entered at the relay that already owns the device, so nothing is forwarded. Applies when the request enters at the owning relay.
  9. The owner delivers. Relay B repeats the authorization check, confirms it still holds the lease and sends the exchange down the device's data socket.
  10. The response returns. The response travels back the same way. Relay-to-relay ordering does not create a global order across streams, and it never authorizes a retry.

If the owning relay stops

  1. The owner stops. Relay B stops. Its device sessions end, and so do the streams that were riding on them. Nothing held in its memory moves to another relay.
  2. In-flight work is not replayed. A request that had already been dispatched ends with an explicit interrupted or unknown outcome. The relay never replays it; the consumer decides whether to try again.
  3. The lease is released or expires. On a clean stop the relay releases its lease at once. After a crash the lease stays in Redis until it expires, 30 seconds by default, and reconnects are refused as owner-busy until then.
  4. The device reconnects. The client retries with backoff. The load balancer hands its new control socket to another relay, here Relay A.
  5. A new owner under a newer fence. Relay A claims the lease. Redis increments the device's owner epoch, so the new owner token outranks the old one, and the device starts a fresh session.
  6. A stale owner is refused. If Relay B comes back still believing it is the owner, its renewal and release compare the full owner token and fail. The device has already rejected the old owner before acknowledging the new one.
  7. Requests find the new owner. The next request performs a fresh owner lookup and is routed to Relay A. Sessions that cannot survive an owner change, such as open filesystem handles, start again.

2. How the daemon on the user's computer connects

The client only ever dials out. It holds two WebSockets in steady state, both authenticated with the device's own certificate, and briefly a third while the data socket is rotated.

  1. Outbound only. The client dials the relay's device listener. The computer opens no inbound port, and the load balancer passes TCP straight through so the TLS handshake ends inside the relay.
  2. Control socket with mutual TLS. The client verifies the relay's certificate and presents its per-device certificate. The relay checks the chain, identity, validity and revocation before it accepts the WebSocket.
  3. Hello, welcome and ownership. The client says hello and the two agree a protocol version. The relay takes ownership of the device and replies with the session, its limits, the heartbeat and rotation policy, and a short-lived single-use ticket.
  4. Data socket with certificate and ticket. The client opens a second outbound WebSocket, again with mutual TLS, and presents the ticket. The owner consumes the ticket once; the certificate and the ticket are both required.
  5. Two sockets in steady state. The relay reports that data is ready and only then admits streams. The control socket carries coordination; the data socket carries every stream's payload.
  6. Heartbeats. The protocol document proposes a control heartbeat every 20 seconds, with the peer counted lost after 60 without a valid reply. A heartbeat does not renew ownership; the lease is renewed separately.
  7. Reconnect with backoff. If the session ends, the client retries with jittered exponential backoff, from 1 second up to 60 by default. A refused certificate or bad configuration is final and is not retried.

Rotating the data socket

  1. Prepare a third socket. Every 300 seconds by default the owner asks for a rotation and issues a fresh ticket. The client opens a replacement data socket, so for a bounded time there are three sockets.
  2. Pause new streams. The owner pauses new stream opens and fixes the list of streams this rotation covers. A request arriving now is held for at most 1.5 seconds, then refused as not dispatched and retryable.
  3. Writes freeze at a fence. Each side stops writing new frames to the old socket and flushes what it had queued. It then reports, for every stream and direction, the last sequence number it sent. That fence cannot change.
  4. Drain to the fence. Each receiver keeps reading the old socket until it has every frame up to the fence, with no gaps, and then reports it has drained. Nothing sequenced travels on the replacement yet.
  5. Commit the replacement. With both drain reports in hand the owner commits. Writers resume on the replacement socket and sequence numbers carry on above the fences, so nothing is replayed.
  6. Retire the old socket. Both sides close the old data socket and the device is back to two sockets. Open streams continue without reopening. Drained means the bytes are accounted for, not that an operation finished.

3. How an agent talks through the relays to the daemon

A request names one device and one service. It is authorized at the relay, routed to the owner, and checked again on the computer before anything local runs.

The relay terminates TLS and can see service traffic. This is not end-to-end encryption.
  1. The agent presents a token. The agent or application, the consumer, sends an HTTPS request that names a device and a service to a relay's public listener, with its access token in a header.
  2. The relay authorizes it. Relay A takes the tenant from the authenticated token and checks the grant for that exact device and service in Redis, atomically, against one consistent catalog revision.
  3. Route to the owner. Relay A is not the device's owner, so it forwards the exchange once to Relay B over the private peer link. Relay B validates the token and the grant again itself. Applies when the request enters at a relay that does not own the device.
  4. Already at the owner. Relay A owns this device, so the exchange stays on one relay. Applies when the request enters at the owning relay.
  5. Down the data socket. The owner opens a logical stream on the control socket and sends the request frames down the device's data socket, each with its stream's sequence number.
  6. The daemon checks for itself. Before running anything the daemon confirms the authorization with the owner, valid for at most 5 seconds, and checks its own local export configuration. Access is the intersection of the grant and the local exports.
  7. Hand-off to the local capability. The daemon hands the request to the configured capability: an MCP server, an ACP agent, a filesystem export or a fixed HTTP forward. Computer use exists but is not enabled in shipped builds.
  8. The response returns. The response returns the same way: data socket, owner relay, peer link if there was one, and back to the consumer.
  9. An acknowledgement is not completion. A transport acknowledgement shows that frames arrived, not that the action completed. If the connection is lost mid-operation the outcome is reported as unknown and is not replayed.
  10. The trust boundary. TLS protects each leg, but the relay terminates it and can see service traffic. This is not end-to-end encryption, and the local allowlist still applies with a trusted relay.
Every part of the diagram, in words

Agent or application (consumer)

What it is
The agent or application that wants to use something on an enrolled computer. It can run anywhere, including the cloud.
What it holds
Its own access token from an external identity provider. It never holds a device certificate or a private relay address.
What it is trusted with
Only what tenant-scoped grants allow: a named device, a named service and the permitted operations.
If it is lost
Its streams end. Work already running on the computer follows that capability's cancellation rules. Nothing is queued for later.

Public load balancer

What it is
The public entry to the relays. It may hand any connection to any relay; no sticky routing is needed.
What it holds
No Agent Uplink state.
What it is trusted with
Reachability only. For device sockets it must pass TCP straight through, so mutual TLS ends inside the relay. Certificate headers forwarded from the internet are never trusted.
If it is lost
No new connections reach the relays until it returns. Sockets passing through it drop and the client reconnects with backoff.

Relay

What it is
A relay server. It serves public HTTPS for consumers, a mutual-TLS WebSocket listener for devices and a private HTTP/3 listener for other relays. The relay that owns a device is the only one that pairs its sockets, admits streams and coordinates rotation.
What it holds
Live sockets, per-stream sequence state and bounded buffers, all in memory, plus its own private keys. It has no catalog of its own.
What it is trusted with
Service traffic. A relay terminates TLS on both legs and can read what passes through it. This is not end-to-end encryption.
If it is lost
Its device sessions and streams end. Devices it owned reconnect and get a new owner; in-memory state is not moved to another relay. The cluster design has been exercised with three relays in local harness runs, and complete cluster acceptance is still open.

Redis (the single authoritative store)

What it is
The only shared storage and coordination authority.
What it holds
The durable catalog (tenants, memberships, identities, grants, device certificate registrations, revocation versions), the signed relay membership records, and short-lived presence, owner leases and one-use tickets. Never private keys, file contents, screenshots, MCP or ACP bodies, or replay buffers.
What it is trusted with
To be the one authority for authorization and ownership. It is not a root of trust: a key that merely appears in Redis proves nothing without a valid signature from the membership authority.
If it is lost
Relays fail closed: readiness goes false, new work is refused and sessions close as their leases run out. The supported profile is one primary with no automatic promotion or failover. In a cluster, a Redis restart, restore or unclear primary needs an operator-approved recovery.

Membership authority

What it is
An operator-run service, separate from the relays, that decides which relay public keys belong to this deployment. It signs one membership record per relay and answers signed checkpoint requests.
What it holds
The membership signing key, which stays outside Redis and outside ordinary relay configuration.
What it is trusted with
Cluster membership only. It cannot enrol a device or grant a consumer anything.
If it is lost
Relays become unready and refuse new work as their signed records lapse (60-second lifetime, refreshed every 20 seconds). A relay that starts while the authority is unreachable stays unready. An outage shared by every relay does not, by itself, make them drop the devices they hold.

Client daemon

What it is
The Agent Uplink client running on the user's computer. It dials out to a relay. Nothing listens for inbound connections on the computer.
What it holds
The device private key and certificate, in protected local storage, and the local export configuration that names what may be reached.
What it is trusted with
The final decision. It checks every operation against the grant bound to the stream and against its own local configuration, so effective access is the intersection of the two.
If it is lost
The device shows as offline and requests for it return a device-offline error; nothing is queued. It reconnects by itself with jittered exponential backoff (1 second rising to 60 by default) and starts a fresh session.

Local capabilities

What it is
What the computer's owner chose to export: MCP servers, an ACP agent, confined filesystem mounts and fixed HTTP forwards. A computer-use adapter exists but is not enabled in shipped builds.
What it holds
Whatever the local service itself holds. A consumer cannot name an upstream URL, a command or a credential; targets are fixed in local configuration.
What it is trusted with
Only requests the daemon has already authorized.
If it is lost
The operation fails or its outcome is reported as unknown. It is not retried automatically.

Public HTTPS

What it is
Consumer requests to a relay's public listener, authenticated with the consumer's access token. Filesystem clients upgrade the same kind of request to a WebSocket.
What it holds
Requests and responses in transit. Tokens travel in headers, never in URLs.
What it is trusted with
TLS protects this leg. The relay at the end of it can read the content.
If it is lost
The request ends. If it had already been dispatched, its outcome may be unknown.

Private peer link (HTTP/3)

What it is
HTTP/3 over QUIC between two relays, opened on demand, with mutual TLS using relay identities that are separate from device credentials. It carries an exchange from the relay that received it to the relay that owns the device.
What it holds
Bounded, framed bytes for the forwarded exchange. The hop budget is exactly one: a relay never forwards onward.
What it is trusted with
Only peers whose key is approved by a current signed membership record. There is no fallback to HTTP/2 or plain TCP.
If it is lost
Before dispatch the consumer gets a retryable error marked as not dispatched. After dispatch the result is reported as interrupted or unknown.

Relay to Redis

What it is
Each relay's authenticated TLS connection to Redis.
What it holds
Catalog reads, atomic authorization and lease scripts, and membership record reads.
What it is trusted with
Atomic scripts. Ownership and authorization are never a check followed by a separate write.
If it is lost
That relay stops admitting work at once (authority calls time out after 2 seconds) and closes sessions as its leases run out.

Signed membership records

What it is
The authority publishes signed records into Redis. Relays read them there and verify each signature against a key the operator installed.
What it holds
Public keys, private-network endpoints and validity windows. No private keys and no root of trust.
What it is trusted with
The signature, not the storage. A successful Redis read never extends a record past its signed expiry.
If it is lost
Records lapse after their signed lifetime and relays stop trusting each other as peers.

Control socket

What it is
The first outbound WebSocket, with mutual TLS. It carries the handshake, stream admission, cancellation, heartbeats, authorization and ownership confirmations, and rotation coordination.
What it holds
Small bounded control messages (32 KiB ceiling). No payloads.
What it is trusted with
The device identity in its certificate, verified before the WebSocket upgrade.
If it is lost
The relay stops admitting operations for that device. A reconnect starts a fresh session.

Data socket

What it is
The second outbound WebSocket, also mutual TLS, admitted only with a single-use ticket issued over the control socket. It multiplexes the payloads of every stream.
What it holds
Binary frames with a sequence number per stream and direction. In a cluster it may be accepted by a different relay, which forwards it to the owner over the peer link.
What it is trusted with
The device certificate and the ticket together. Neither alone attaches a data socket.
If it is lost
While the control socket is healthy the owner authorizes a replacement and resumes from retained sequence state, within a bounded number of attempts.

Replacement data socket

What it is
The temporary third socket during a rotation. The overlap is bounded: 30 seconds in total, and the candidate must attach within 10.
What it holds
Nothing sequenced until the rotation commits.
What it is trusted with
The same as the data socket: the device certificate plus a fresh single-use ticket.
If it is lost
If it fails before the commit, the rotation is aborted and the old socket carries on.

Local hand-off

What it is
The daemon calling the configured local service on the same computer: a supervised process over stdio, a fixed local HTTP endpoint, or its built-in filesystem server.
What it holds
The request and response for that operation.
What it is trusted with
Fixed targets from local configuration. The consumer's credential is never forwarded to the device.
If it is lost
The operation fails or is reported as outcome unknown.

Permissions are not implied by connectivity

Authority is scoped by tenant, principal, device, service and permitted operations. Local configuration defines exports. A connected computer is not an unrestricted remote desktop or shell.

Two sockets in steady state

Each device uses one control and one data socket. Ordered data-socket rotation permits a bounded temporary third socket while old streams drain; the daemon scene above steps through it. Transport acknowledgements do not prove an application side effect completed.

Finite echo retention

Current main implements owner-issued STREAM_FORGET for successfully completed finite echoes and explicitly rejected opens, reclaiming connector retention only after the required terminal and acknowledgement evidence. Cleanup waits while rotation or recovery holds the stream roster. Rotation fencing now includes the dispatched FIN and preserves completed echoes until the attempt finishes.

These are scoped fixes, not complete echo or transport acceptance. Repository regression gates cover more than 128 sequential echoes and echoes crossing rotations; they were not rerun for this website review. An echo that ends another way (a RESET, a cancellation, an authorization invalidation, a failed dispatch, a consumer that went away or the operation timeout) answers the consumer at once and is reclaimed under the same evidence; one still lacking that evidence after 60 seconds closes the session. See support boundaries.

State and recovery

Redis is the authoritative catalog and coordination store. Process-local sockets and in-flight work are ephemeral. The supported coordination profile uses one authoritative Redis primary; replication is not a promise of automatic, lossless failover. Recovery must reconcile revocations and fence old ownership.

A Redis restart changes its run identity. Current main has a narrow, single-relay path to keep the namespace after an in-place restart from the same durable AOF: a serving relay can verify its continuity token, or an operator can attest the restart using rebind-redis-run. See the prerequisites and exclusions. Neither path is backup-restore or failover recovery. Cluster Redis restarts, restores and ambiguous authority still need externally approved recovery; the membership authority that ships does not activate recovery. A fresh namespace is a new deployment, not restoration of old authorization. Never delete authority keys to bypass fencing.

Cluster readiness

In current main, /readyz and public admission both require a non-empty verified transport key-pin set, alongside membership and peer readiness. If those pins are withdrawn, readiness fails and public work is refused even before the next peer refresh. Restoring pins alone is not enough if another readiness condition still fails.

This check applies to the cluster peer runtime, not the non-cluster M1/M2 profile. Readiness is an admission check, not proof of an end-to-end service operation or full cluster acceptance. Source and regression tests cover pin withdrawal and recovery; deployment-specific verification remains required.

Trust boundary

The relay terminates encrypted connections and is trusted with service traffic. Agent Uplink does not claim end-to-end encryption through an untrusted relay.

Private keys stay outside the catalog. Diagnostics should expose identifiers, phases and counters, not payloads or credentials. Never automatically replay an ambiguous click, write or agent prompt after losing its outcome.
