# Axum runtime, device mTLS, and CLI

Status: runtime implementation design, 2026-09-09. M1 implements the client `config check`, `credentials create`, `credentials import` and foreground `connect` commands; the relay implements `serve` with Axum HTTPS, both device mTLS WebSockets and Redis/JWT authority, plus the read-only `check-serve-config --config PATH` dry run for that serving configuration. Legacy `check-config` remains supported. See [M1 evidence](m1-harness.md). The supervisor status IPC, `status`, and `doctor`'s IPC check are implemented (M6-06; [Supervisor status IPC](#supervisor-status-ipc)), and so is `disconnect` (M0-03) and `credentials renew` (M0-07; [Credential renewal](#credential-renewal)); enrollment and generic adapters below remain planned. M2 rotation and M7 cluster work have separate current evidence in their verification documents. The local-only doctor slice is implemented and locally verified as described below.

The M1 relay uses one bounded actor for its finite echo sessions; the target per-device actor architecture below will isolate richer M2/M7 state. M1 owner fields expire logically within durable Redis device hashes; physical TTL lease namespaces are a later cluster change. Normal startup cannot initialize missing authority metadata. Recovery requires an operator to reconcile durable authorization history; changing the owner incarnation does not verify an arbitrary restored backup.

This document fixes the runtime boundaries. [protocol.md](protocol.md) defines socket pairing and rotation; [cluster.md](cluster.md) defines peer trust, routing, ownership, and Redis failure behavior; [acp.md](acp.md) defines remotely controlled agent exports.

## Three listener roles

| Role | Transport and implementation | Authentication | Exposure |
| --- | --- | --- | --- |
| Consumer API | HTTPS HTTP/1.1 and HTTP/2, Axum; consumer filesystem WSS initially uses HTTP/1.1 upgrade | Scoped OAuth access token; authorized user/consumer principal | Public API hostname, e.g. `api.example.test:443` |
| Device tunnel | WSS over HTTP/1.1 and TLS 1.3, Axum behind an in-process rustls acceptor | Mandatory device client certificate on **control and every data connection** | Separate device hostname/listener, e.g. `devices.example.test:443` |
| Cluster peer API | HTTP/3 over QUIC/UDP and TLS 1.3; dedicated `quinn` + `h3` + `h3-quinn` adapter | Mandatory relay certificate plus approved peer identity/key record | Private node addresses, e.g. UDP `8443`; reachable between relay nodes only |

Ports above are examples, configurable independently. Separate sockets/listener configurations are the initial deployment profile; sharing a port through SNI is a later deployment capability requiring its own tests. The public consumer listener never exposes private peer routes. Consumer OAuth tokens cannot authenticate a device or a relay peer.

Axum is the web framework for public HTTP and device WebSockets. Its documented `serve` path supports HTTP/1 and HTTP/2; HTTP/3 needs a distinct integration, not a configuration flag on `axum::serve`. Implement a small peer HTTP/3 transport adapter calling shared typed application services. Do not require public Axum routes, WebSocket extractors, or Tower body assumptions to work unchanged over HTTP/3. Sources: [Axum serve](https://docs.rs/axum/latest/axum/fn.serve.html), [Axum WebSockets](https://docs.rs/axum/latest/axum/extract/ws/), [h3](https://docs.rs/h3/latest/h3/), [h3-quinn](https://docs.rs/h3-quinn/latest/h3_quinn/).

### Bounded listener connection permits

Both public listeners supervise at most 64 concurrent TLS handshakes and HTTP connections by default (`listener_max_connections`, `1..=4096`, applied to each listener separately), and one permit is held for the whole HTTP connection. A permit is therefore bounded in time as well as in count by three validated `ListenerTimeouts` values, so an anonymous consumer connection (or a connection presenting one valid device certificate) cannot hold a permit by completing the TLS handshake and then staying silent:

| Bound | Default | Accepted range | Phase it covers |
| --- | --- | --- | --- |
| `handshake_timeout` | 10 s | 100 ms..=300 s | TCP accept until the TLS 1.3 handshake completes |
| `pre_request_timeout` | 15 s | 100 ms..=300 s | Handshake completion until the connection dispatches its first complete HTTP request: HTTP/1-versus-HTTP/2 sniffing, the HTTP/2 preamble, and the first request head |
| `http1_header_read_timeout` | 10 s | 100 ms..=300 s, not above `pre_request_timeout` | Each single HTTP/1 request-head read, including an idle keep-alive gap between requests |

A silent connection therefore holds a permit for at most 25 seconds by default, then is closed and returns it. The pre-request bound is disarmed permanently by the first dispatched request, so an established device WebSocket upgrade, an in-flight consumer request, and a streaming response body are never closed by it; `http1_header_read_timeout` is armed by Hyper only when it can read a new request head, so it does not apply during an in-flight request, a streaming body, or after an upgrade. HTTP/2 has no header-read deadline of its own, and `hyper_util`'s protocol sniffer has no deadline at all, which is why the pre-request bound is enforced by the listener rather than delegated to Hyper. Hyper discards a configured header-read deadline unless a timer is installed on its builder, so the listener installs a Tokio timer on both the HTTP/1 and HTTP/2 builders. Raising the permit count is not a substitute for these deadlines. An invalid value fails closed: the listener returns a typed error and releases the socket instead of accepting with an unbounded permit.

### Connections over the limit (M6-C153)

A connection that arrives while every permit is held is **refused explicitly, never reset**. Applied by default pending owner confirmation (2026-09-25):

1. **Refusal margin.** The listener accepts up to `listener_refusal_margin` (default 16, `0..=256`) extra connections only to refuse them. Each completes TLS (the device listener still requires a valid client certificate), reads one request head and at most 64 KiB of body, answers, and is closed with a TLS `close_notify`:

   ```
   HTTP/1.1 503 Service Unavailable
   retry-after: 1
   connection: close
   {"code":"CONNECTION_LIMIT","execution":"not_dispatched",
    "message":"relay listener connection limit reached",
    "retryable":true,"retry_after_ms":1000}
   ```

   The request is never routed, so nothing is dispatched to a device and no authentication is attempted. HTTP/2 gets the same answer followed by GOAWAY. A device WebSocket upgrade gets the same `503`; the client treats it as a retryable transport failure and reconnects with its usual back-off. The whole over-capacity connection is bounded by a 5 s refusal deadline (`DEFAULT_REFUSAL_TIMEOUT`); a peer that has not finished by then is dropped and frees the slot.
2. **Backlog when the margin is full.** While both the permits and the refusal slots are taken, the listener does not call `accept`. Further connections wait in the kernel listen backlog (128 as the relay binds it through Tokio, capped by the OS `somaxconn`; measured `kern.ipc.somaxconn` 128 on the macOS test host) and are served or refused as slots free. The listener never accepts a socket and then drops it unanswered; only the kernel can refuse a connection, when its backlog is full.

**Why this option.** The owner brief offered three: (a) complete TLS within a small margin and answer `503`; (b) accept into a bounded queue and hold each connection until a permit frees, then `503` on timeout; (c) leave excess connections in the kernel backlog. Option (c) alone gives a client no answer at all: under a keep-alive flood the served connections never close, so a backlogged client waits until its own timeout, which is no more distinguishable from a dead relay than a reset. Option (b) holds a file descriptor and a TLS session per queued connection for the whole wait and still ends in the same `503`, so it costs more than (a) for the same answer. Option (a) is the smallest amount of work that yields a distinguishable, retryable answer, and its cost is bounded by the margin: at most 16 extra TLS handshakes and 16 x 64 KiB of buffered body at any moment, each for at most 5 s. Falling back to (c) when the margin is full removes the remaining reset without adding work. Setting `listener_refusal_margin = 0` selects pure (c). The 64 limit is unchanged: no measurement justifies another value, and keep-alive connections still count against it for as long as they stay open.

**Accept errors (M6-C155).** A transient `accept` error no longer ends the listener. Resource exhaustion (`EMFILE`, `ENFILE`, `ENOBUFS`, `ENOMEM`) is logged at `warn` with a fixed `class`, rate limited per class. The listener then releases the slot and waits `ACCEPT_ERROR_BACKOFF` (100 ms), so a connection that cannot be accepted does not spin the loop, and accepts again. A peer that aborted or reset before `accept` (`ECONNABORTED`; on Windows `WSAECONNABORTED` and `WSAECONNRESET`) is retried immediately with no pause and logged only at `debug`, as axum does. A backoff there would let a client that repeatedly connects and resets throttle the listener to about 10 accepts per second. Any other `accept` error still ends the listener with `TransportError::Accept`. Serving startup prints a warning when the soft `RLIMIT_NOFILE` is below `2 x (listener_max_connections + listener_refusal_margin)`. **TLS failures on refused connections (M6-C156)** are logged through the same labelled, rate-limited `TLS handshake refused` path as on served connections.

**Operator signals.** Each listener logs `refusing connection over the listener connection limit` at `info` with `phase=listener_capacity`, `listener`, `max_connections` and a `suppressed` count, rate limited like the TLS refusal lines (20 lines per 10 s per listener). A load-balancer health check that lands while a listener is full also gets `503 CONNECTION_LIMIT`, distinguishable from `/readyz`'s `503 {"status":"unready"}` by its body. Since M6-C193 the refusal count is also the `/metrics` series `tunnel_relay_listener_capacity_refusals_total{listener}` (below).

### Turnover while the consumer listener is full (M6-C193)

A permit is held for a whole keep-alive connection, and a busy keep-alive connection never closes by itself. Before M6-C193, a client whose keep-alive connections held every consumer permit kept them for the whole of its flood, and every client that connected later was refused `CONNECTION_LIMIT` on every attempt (measured locally: 0 of 198). The listener takes a permit at accept, before TLS and before any bearer token is read, so it cannot share permits by user. **Decision (coordinator, under the owner's delegation, 2026-09-27): option (b), permit turnover while the listener is full.** A per-source quota (c) is left to the deployment edge, because behind Fly's proxy the relay may not see client addresses; a per-principal share (d) waits on M6-C126.

* **Pressure.** The consumer listener is under pressure while a connection has arrived with every permit held within the last second (`PRESSURE_WINDOW`). A pressure episode starts with the first such arrival after a quiet second. With `listener_refusal_margin = 0` no connection over the limit is accepted, so the listener never sees pressure and nothing turns over.
* **Turnover.** Under pressure, a served connection is closed after its current response once it has lived its own age budget or served `listener_turnover_max_requests` (default 1,000, `1..=1000000`) requests, both counted from the later of its own start and the start of the episode. The age budget is drawn once per connection, uniformly between 50% and 100% of `listener_turnover_max_age_seconds` (default 10, `1..=3600`), so 5 -- 10 s by default; the effective minimum age is therefore half of `listener_turnover_max_age_seconds` (coordinator decision under the owner's delegation, review of PR #222). With one fixed age, every connection open when pressure began reached it at the same moment, every replacement then started at that burst instant, and the bursts repeated every 10 s for the whole flood: the hosted fairness runs 36281427390 / 36281441437 recycled about 64 connections every 10 s and almost none in between. The jitter makes permits free continuously. HTTP/1.1 closes with `Connection: close` on that response, after its body; HTTP/2 closes with a graceful GOAWAY, and every stream already accepted runs to its end. A `101 Switching Protocols` response is never marked, so an upgraded connection (a consumer WebSocket or `stream`) is never recycled, and no response is cut. Outside pressure nothing changes.
* **Hand-off.** Turnover alone mostly returned permits to the flood: the recycled client's reconnect is usually already in the listen backlog when its permit frees. Measured at small scale (4 permits, 6 flood workers, one client retrying every 20 ms): 80 recycled permits in 20 s, and the late client was refused 855 times out of 855. So a connection accepted over the limit on the consumer listener first waits up to `HANDOFF_WAIT` (500 ms), before any TLS work, in the permit semaphore's FIFO queue, holding the `listener_refusal_margin` slot it was accepted with. If a permit frees in that time, the connection is served; otherwise it gets the same `503 CONNECTION_LIMIT` as before (M6-C153), with that refusal's own 5 s deadline starting after the wait. Waiting clients get freed permits in arrival order, in proportion to how many connections each has waiting. In the same test the late client was served within 0.5 s with no refusal.
* **The hand-off slows refusals, and that is the point.** Nothing at accept time identifies the caller, so fairness against a flood that does not back off can only come from slowing that flood's reconnects. A margin slot that waits 500 ms refuses at most about twice a second: in the hosted fairness runs refusals fell from about 695/s to 25 -- 30/s, and the relay's CPU fell with them. **The cost:** under sustained over-limit arrivals faster than about `2 x listener_refusal_margin` per second (32/s with the defaults), the excess waits in the kernel listen backlog, and beyond the backlog a connection can see a connect timeout (SYN retransmits) instead of the explicit `503`. Only clients that already ignore `retry_after_ms` reach that rate; a client that backs off still gets the `503`, and a SYN retransmit still lets it retry. Mitigate at the edge with per-source rate limiting and connection limits ([deploy-fly.md](deploy-fly.md) section 1), and with a larger `listener_refusal_margin` if needed. **Rejected alternative** (review of PR #222, coordinator decision under the owner's delegation, then reversed on measurement): a separate 16-slot hand-off queue with an immediate `503` through the margin when it was full. The flood kept the queue full, so refusals returned to 557 -- 1,335/s, A's served rate fell to 416 -- 1,045 OK/s, and a B client that connected during the flood went unserved for the whole 50 s window in both hosted runs (36283563574, 36284228822); load without back-off fell 1,994 -> 760 -> 599 OK/s again (36283566038).
* **Scope.** Only the consumer listener turns over. The device listener serves the CLI's control and data WebSockets and never recycles or hands off; its over-limit behaviour is M6-C153's.
* **Signals.** `/metrics` has `tunnel_relay_listener_under_pressure{listener}`, `tunnel_relay_listener_pressure_episodes_total{listener}`, `tunnel_relay_listener_capacity_refusals_total{listener}`, `tunnel_relay_listener_fairness_handoffs_total{listener}` and `tunnel_relay_listener_fairness_recycled_total{listener}`, with `listener` one of `consumer` and `device`. They are counts and a flag only.

This bounds how long a waiting client is shut out; it does not give each user an equal share. A flood with many connections waiting still gets most freed permits, in proportion to its demand. A per-user share of the listener is M6-C126's decision.

### TLS session resumption on the consumer listener (M6-C194)

Turnover and `CONNECTION_LIMIT` refusals make clients reconnect, and each full TLS 1.3 handshake costs the relay a certificate signature. The public consumer listener therefore issues TLS 1.3 stateless session tickets (two per handshake) when it is not an mTLS listener (no `consumer_tls_client_ca`). The ticket key is generated in memory by rustls's `Ticketer`, rotates every six hours, and is never written, logged or shared between relays; a client that resumes on another relay gets a full handshake. Early data (0-RTT) stays off, so a resumed connection cannot replay a request. The device and peer listeners, and a consumer listener with a client CA, keep resumption disabled, as below. Measured server CPU per handshake (in-memory rustls, M1 Pro, the `handshake_cost` example of the `tunnel-transport` crate): RSA-2048 full 604 -- 607 µs, resumed 73 -- 74 µs; ECDSA P-256 full 78 -- 79 µs, resumed 73 -- 74 µs. An ECDSA P-256 server certificate is the operator recommendation ([operator.md](operator.md#22-relay-listener-identities)).

The two steady-state WebSockets belong to each CLI device connection. Peer QUIC connections and consumer connections are separate. Private HTTP/3 forwarding does not add a third steady-state device socket. During data rotation, one control plus old and candidate data sockets remain bounded by the existing overlap deadline.

### TCP_NODELAY

Every TCP socket that carries request/reply traffic has Nagle's algorithm disabled (task row M6-C124):

| Socket | Where it is set | Gate |
| --- | --- | --- |
| Relay consumer and device listeners, every accepted socket | `tunnel-transport` `set_accepted_nodelay`, before the TLS handshake; a failure (a peer that already reset) is logged at debug and the connection is still served; it is counted only when `AcceptedSocketDiagnostics` are attached (tests), not in production | `accepted_sockets_have_nodelay_set_by_default` |
| Device control and data WebSockets (outbound) | `tunnel-client` `open_socket`, tokio-tungstenite `disable_nagle = true` | `open_socket_sets_tcp_nodelay` |
| Catalog Redis lanes, the recovery scanner and the primary connection | `tunnel-catalog` `catalog_connection_info` (redis-rs defaults it off) | `catalog_clients_disable_nagle_on_every_connection` |
| Relay membership runtime's checkpoint-authority HTTPS connection (TCP, then TLS and HTTP/1.1; not Redis) | `membership_runtime.rs` (already set before this change) | none added |

Without it, a small write that followed an unacknowledged one waited for the peer's delayed ACK, which is 40 ms on Linux: the hosted load experiment's single echo worker went from p50 42.4 ms to 1.65 ms when it was set, and a 64 KiB echo from 23.8 to 266.6 requests per second. Bulk writes fill whole segments, which Nagle never delayed, so the option costs bulk transfer nothing measurable. Measurements and runs: [soak-2026-09-26.md](soak-2026-09-26.md#update-tcp_nodelay-m6-c124). The private metrics listener and test-only proxies are not on the request path and are left at the platform default.

## Device authentication contract

1. The CLI verifies the relay certificate chain and expected DNS name against its configured server trust bundle. Development uses a dedicated fixture CA. There is no `--insecure`, anonymous TLS fallback, certificate auto-accept, or plaintext production endpoint.
2. The device TLS acceptor requires a client certificate and verifies the chain, validity, intended client usage, and proof of possession before accepting HTTP requests. Configure the rustls verifier to require authentication; never use `allow_unauthenticated` on this listener.
3. Parse the approved certificate identity and map its public-key fingerprint/credential ID to an active durable device credential record. That record supplies the tenant and device ID. A valid certificate from the device issuer alone is insufficient if its credential is unknown, disabled, or not assigned to that device.
4. The acceptor constructs an internal `VerifiedTlsIdentity { role, principal_id, credential_id, public_key_fingerprint, certificate_expires_at }`. Authentication middleware resolves current device state and inserts an `AuthenticatedDevice` extension. These types have constructors restricted to the verification boundary.
5. Control upgrade authorizes the device, acquires ownership as specified in [cluster.md](cluster.md), and binds the connection epoch to the credential ID. Data upgrade repeats mTLS authentication and verifies the one-use pairing ticket against the same device, credential, session, epoch, and generation.
6. A ticket is supplemental attachment authority, never a replacement for mTLS. A stolen ticket and a different valid device certificate cannot attach. A caller-supplied device/tenant name cannot override the certificate mapping.
7. Every new stream also requires consumer grants and device-local export policy. mTLS proves the device identity; it does not grant the caller filesystem, MCP, CUA, or ACP permissions.

`X-Client-Cert`, `X-Device-ID`, forwarded certificate headers, URL parameters, and peer IP addresses never create `VerifiedTlsIdentity`. Strip or ignore them at the edge. If a different relay accepts a data socket, verified identity is conveyed only through the authenticated, typed peer envelope defined in the cluster contract; the owner checks the device/credential and attachment binding again.

Use separate trust purposes for public server authentication, device client credentials, and cluster peer credentials. Prefer separate issuers or constrained intermediates; any shared root requires tested role restrictions and registry checks. A device certificate must fail cluster admission, and a relay certificate must fail device admission. The CLI needs no Redis access and does not accept Redis membership as device enrollment authority.

Disable TLS resumption and early data on the initial device mTLS profile, so every socket establishes fresh certificate evidence (the anonymous-TLS consumer listener resumes, without early data: M6-C194 above). Disable QUIC 0-RTT on peers. Resumption can be added only with revocation-aware identity restoration and replay tests. No mutation or ticket consumption may occur from early data.

## Provisioning, renewal, and revocation

Initial network development uses externally provisioned credentials. An administrator configures trusted issuers and creates the tenant/device credential binding; the CLI creates its private key locally and exports a CSR. An approved issuer signs the CSR; the CLI imports only a matching certificate chain and its server trust bundle. Certificate import verifies that the issued public key matches the pending local key. It never changes server trust based on an unauthenticated network response.

The first production enrollment flow is a separate implementation gate:

1. An authenticated tenant administrator creates a short-lived, one-use enrollment authorization for one device. The authorization binds the tenant, requested device record, audience, expiry, and enrollment purpose.
2. The CLI contacts a narrow enrollment route on the **server-authenticated consumer HTTPS listener** using an independently supplied CA bundle or platform-trusted public server certificate. An unenrolled device cannot yet authenticate with a client certificate; this route cannot open control/data sockets or invoke services.
3. `enroll` reads the authorization from protected stdin or a secret-store reference, creates its private key locally, and submits a bounded CSR. Never pass codes in process arguments, URLs, logs, or copied command examples.
4. The enrollment service verifies authorization, CSR possession, and allowed certificate fields; it supplies authoritative identity/tenant bindings and atomically consumes the authorization with credential creation. The device cannot choose another tenant or certificate role in its CSR.
5. Return the public certificate chain and enrollment receipt; validate the chain/key/identity, persist credentials atomically, and connect using mTLS. Retried enrollment resolves through a bounded receipt/idempotency mechanism, not an unscoped reusable enrollment code.

Keep the issuing private key in an external CA/signing service or a narrowly isolated issuer component; it is not a relay configuration value or Redis entry. Initial externally provisioned credentials avoid implementing a CA in the transport milestone. Automated enrollment requires a selected issuer, issuance profile, issuance audit, and recovery tests before it is advertised.

The initial credential store may use owner-only files with atomic replacement and tested permissions: private directory/file modes on Unix, explicit owner ACLs on Windows. OS keychain/non-exportable key integration is a separate supported-backend gate. Configuration stores credential references, certificate paths, and trust-bundle paths, not PEM private-key text. Never silently downgrade from an unavailable selected secure store. Diagnostic output may show key fingerprints and certificate expiry, never private-key bytes.

Renewal uses the existing authenticated device plus current authorization and a new local CSR/key. Publish the new credential as an explicit overlap with an absolute deadline, then drain current work and close the old socket pair before connecting a fresh control/data epoch with the new credential. This deliberate reconnect may end sessions; expose pending mutations as `outcome_unknown` where required. Do not mix two credential IDs in one epoch or preserve an old certificate indefinitely to keep a stream open.

**What is implemented (M0-07)** is the local, externally issued form of this: [`credentials renew`](#credential-renewal) writes the new key and CSR, the operator carries the CSR to the issuer, and the issued certificate is checked and swapped in. There is no overlap inside one supervisor: a running `connect` keeps the pair it started with, and the new one is used from the next start, whose fresh control/data epoch presents only the new credential. The issuer protocol, the overlap deadline and the automatic drain above remain the enrollment gate's (M6).

Data-socket rotation every 300 seconds and certificate renewal are independent. The connection actor enforces certificate expiry even on an already-open control socket. Revocation closes affected control/data sockets and stops new dispatch independently of socket rotation; already-dispatched side effects retain their actual or unknown outcome. Bound revocation propagation and behavior on stale authorization state through the cluster/policy contract. Short-lived certificates reduce exposure but do not replace revocation checks.

## Proposed CLI surface

Keep the existing binary name `tunnel-client`. `check-config [PATH]`, `config check`, `credentials create`, `credentials import`, `connect`, `doctor`, (since M6-06) `status`, (since M0-03) `disconnect` and (since M0-07) `credentials renew` are implemented today, and they select the exit statuses in the client exit-code table below. `enroll` and `doctor --network` are **not** implemented; `--network` is rejected rather than ignored, by `doctor` and `status` alike. The following is the command contract, and the unimplemented rows are not runnable examples of delivered features.

| Command | Defined behavior |
| --- | --- |
| `tunnel-client config check --config PATH` | Parse and validate local configuration without network calls or service startup; retain `check-config [PATH]` as an alias |
| `tunnel-client credentials create --config PATH --csr-out PATH` | Generate a pending local key, write a public CSR without overwriting an existing credential |
| `tunnel-client credentials import --config PATH --certificate PATH --server-ca PATH` | Validate/import the certificate for the pending key and trusted server bundle from explicit local inputs |
| `tunnel-client enroll --server HTTPS_URL --code-stdin --server-ca PATH --config PATH` | Perform the gated enrollment flow above; omit `--server-ca` only for platform-trusted public PKI |
| `tunnel-client connect --config PATH [--no-reconnect]` | Foreground supervisor; establish the mTLS socket pair, register fixed exports, and run until graceful shutdown. **Reconnects by itself (M6-C23):** a retryable end of session -- relay unreachable, a lost or closed session, a handshake deadline -- is retried with bounded, jittered exponential backoff; a terminal one -- bad configuration, a refused certificate on either side, a protocol violation -- exits at once with its status. Policy in the profile's `[reconnect]` table; `--no-reconnect` restores exit-on-first-failure. See [Reconnecting `connect`](#reconnecting-connect). Stops on SIGINT or SIGTERM in every phase; see [Stopping `connect` and `serve`](#stopping-connect-and-serve) |
| `tunnel-client status --config PATH [--json]` | Read the local supervisor's redacted status through authenticated local IPC; does not start a tunnel. **Implemented (M6-06)**; see [Supervisor status IPC](#supervisor-status-ipc) |
| `tunnel-client doctor --config PATH [--json]` | Check local config, credential/key match, permissions, expiry, and local IPC; no exports are invoked |
| `tunnel-client doctor --config PATH --network --json` | Additionally test DNS, server verification, mTLS, and a bounded non-owning readiness route; does not acquire a device epoch |
| `tunnel-client credentials renew --config PATH --csr-out PATH [--discard-pending] [--json]` | Step one of a renewal: write a new private key beside the current one (`<key>.renew-pending`, `0600`, in the key's `0700` directory) and a CSR for it, never touching the current pair and never overwriting a file. A renewal already pending is refused (`RENEWAL_PENDING`, `2`) unless `--discard-pending` replaces it. **Implemented (M0-07)**; see [Credential renewal](#credential-renewal) |
| `tunnel-client credentials renew --config PATH --certificate PATH [--json]` | Step two, after the operator has carried the CSR to the external issuer: check the issued certificate as `credentials import` does, against the pending key, the device role and the clock, plus that it comes from the current certificate's issuer, then swap the pair in by a crash-safe rename sequence. A running `connect` keeps its pair until it is stopped and started (`disconnect` or the service manager). **Implemented (M0-07)** |
| `tunnel-client disconnect --config PATH [--json] [--timeout SECONDS]` | Ask the same-user supervisor, over its socket, to stop; it takes the orderly stop SIGTERM takes (drain bounded by `rotation.handshake_timeout_seconds + rotation.overlap_seconds`, then both sockets closed and children reaped). `--timeout` (default `30`, `1`--`3600`, a trailing `s` accepted) bounds only how long this command waits for the supervisor to stop answering. **Implemented (M0-03)**; see [Supervisor status IPC](#supervisor-status-ipc) |

Common future flags: `--config PATH`, `--json`, `--log-level LEVEL`, `--log-format text|json`, and `--timeout DURATION` for bounded commands. `connect --rotation-interval 300s` proposes an override within validated relay limits; the effective value is frozen for the epoch and reported in status. Precedence is explicit flags, configuration file, then documented defaults. Do not introduce arbitrary environment-variable overrides of trust or credential values.

Configuration includes a device endpoint URL, credential reference, server trust reference, rotation/backoff/drain policy, and named export definitions. It rejects credentials in URLs, cleartext non-fixture endpoints, unknown fields, invalid timing relationships, and unsafe export roots. Configuration edits take effect after validation on explicit restart; live reload is deferred to avoid partially changing grants and identity mid-session.

`connect` stays in the foreground initially; systemd/launchd/Windows service integration can supervise it later. Only one local supervisor may hold a profile's credentials/runtime lock. Same-user local IPC uses an owner-restricted Unix socket or Windows named pipe with a tested ACL; never expose unauthenticated local TCP administration. The command must fail clearly if the requested supervisor is absent.

Remote agents may invoke only locally configured exports. The CLI has no remotely supplied executable path, arbitrary shell command, or generic TCP proxy mode. A named ACP export selects a fixed local agent and approved launch configuration; [acp.md](acp.md) specifies request handling and permissions. ACP is an application service carried by the data channel; it cannot become a tunnel-control command.

### Client exit codes

These are the exit statuses `tunnel-client` selects, and they are implemented rather than proposed. `Cause::exit_code` in `crates/tunnel-client/src/main.rs` is the authority.

**`Cause::exit_code` is the authority for everything except two paths, which are named here because "the authority" would otherwise be wrong.** `doctor` computes its own statuses in `crates/tunnel-client/src/doctor.rs` (`0`, `2`, `3`) and returns from `main` before the async command runner, so it never reaches `Cause`; and a failure to install the process crypto provider returns a bare `ExitCode::FAILURE` (`1`) with a message and **no diagnostic code**, because it happens before argument parsing and before any `--json` contract exists. Both are consistent with the table below; neither is derived from it.

**This table is a copy, and since M6-02 it is checked against the code.** `scripts/m6-release-artifact.py verify --check docs` parses `Cause::code` and `Cause::exit_code` out of `crates/tunnel-client/src/main.rs` and fails unless every cause appears in exactly one row below whose status is the one the source selects, and unless every status the source produces has a row; its controls edit this table and the source in turn and require it to go red. It does not check the *Meaning* or *What the operator does* columns, nor `doctor`'s own statuses (those are executed instead, by [the operator guide](operator.md#6-diagnostics)). Also checked mechanically: `tunnel_client::CLI_DIAGNOSTIC_EXIT_CODES` is the single definition of the set of statuses, `every_exit_status_is_in_the_published_vocabulary` fails if any cause maps outside it, `the_cli_and_the_library_publish_the_same_diagnostic_code` pins `Cause::code` against `ClientError::code`, and `scripts/m0-guard-exit-codes.py` holds each individual mapping to its meaning with a named witness test. A reviewer changing a status must still edit this table by hand; the docs check then says whether the edit matches.

`7` was added by task row M0-03. A refused-before-dispatch outcome is neither a network failure (`4`) nor a defect (`1`): nothing is wrong, something else holds the slot.

**Exit `6` is documented and unreachable.** No path in `tunnel-client` constructs an ambiguous-outcome cause today, so nothing can produce `6`. It is listed here because the ambiguous-mutation contract is a design requirement and the code is reserved for it; it is deliberately absent from the `Cause` enum, because an enum variant nothing constructs is a surface that reads as covered and is not. Closing the gap means giving the ambiguous-outcome path a producer, not adding the variant.

The **relay** does not use this table. `tunnel-relay` exits `0` or `1` per its bootstrap behavior (see the dry-run section below), plus `130` when a stop request ends `serve` before an orderly completion or a second one abandons a writing command -- the one status it shares with the client, with the same meaning (see the next section). Wiring the relay to the rest of this vocabulary waits for relay CLI parsing and its compatibility tests.

Terminal causes exit without a retry loop; retryable ones are retried by `connect` itself unless reconnect is off (M6-C23). **With reconnect on, statuses `4`, `5` and `7` reach a supervisor only in three cases:** `reconnect.max_attempts` was reached (the last attempt's status, with `gave up after N consecutive reconnect attempts` appended to its message), `OWNER_BUSY` on a first attempt or outside the stale-lease window, or `--no-reconnect` / `enabled = false`. Which cause is which, and why, is [Reconnecting `connect`](#reconnecting-connect).

### Stopping `connect` and `serve`

**Implemented and measured (M6-C23, M6-C27, M6-C29).** Both `tunnel-client connect` and `tunnel-relay serve` treat **SIGINT and SIGTERM as one stop request** and take one orderly path for both. SIGINT is what Ctrl-C sends; SIGTERM is what systemd and launchd send to stop a service by default. For `connect`, a `disconnect` request on the supervisor socket (M0-03, [Supervisor status IPC](#supervisor-status-ipc)) is a third spelling of the same request: it enters the same select, with every bound and the second-request rule below, and its diagnostics name it `disconnect`. Before M6-C23 the only handler was a `tokio::signal::ctrl_c()` future armed after `connect` had connected and after `serve` was serving, so SIGTERM killed either binary in every phase with no output, and SIGINT during the client's handshake or the relay's startup took whatever disposition the process inherited.

The handlers are armed **first**: `connect` before it reads the profile, `serve` before it reads its configuration. What a stop request then does depends only on the phase:

| Binary and phase | Outcome |
| --- | --- |
| `connect`, before the session is ready (profile loaded, TCP connect, TLS, WebSocket upgrade, HELLO/WELCOME, owner fence, data socket, DATA_READY) | the attempt is cancelled through its cancellation token and allowed to unwind (bounded at 2 s, so its sockets are closed by their owner), then exit **`130` `CANCELLED`**, message `SIGTERM received before the session was ready; the connect attempt was cancelled` (or `SIGINT ...`), as the `--json` error event or on stderr. Measured 1--6 ms from the signal to the exit. **The ready boundary is deterministic:** the select that races the attempt against the stop request is `biased` toward the attempt, so an attempt that completes in the same poll -- `connect_m2` has already published `Readiness::Ready` -- is a ready session and takes the next row; so does one that completes during the unwind before it observed the cancellation |
| `connect`, **waiting to reconnect** (in the backoff delay between attempts; M6-C23) | the wait ends at once -- it races the stop request, `biased` toward it -- and `connect` exits **`130` `CANCELLED`**, message `SIGTERM received while waiting to reconnect (attempt N, after TRANSPORT_ERROR); no session was live`. Nothing needs draining: the previous session's connector was joined and its MCP children reaped before the wait began. Measured under 1 s from the signal with a delay of at least 2.5 s left (`crates/tunnel-client/tests/reconnect_cli.rs`). A stop during the next attempt's handshake is the row above, with the same status |
| `connect`, session ready -- including a data rotation or a retained recovery in progress, because one select loop runs for the whole life of the session | orderly stop: cancel, join the supervisor (both sockets closed, handlers dropped, so MCP and ACP sessions end and each child's process group is killed) **bounded by the profile's `rotation.handshake_timeout_seconds + rotation.overlap_seconds`** (40 s with the defaults), then wait up to **5 s** for supervised MCP children to be **reaped** (M6-C29), then print the `stopped` event with `"signal":"SIGTERM"` (or `SIGINT`, or `disconnect`) and exit **`0`**. A join that overruns its bound exits **`130`** (`the orderly stop SIGTERM began did not complete within 40 s; exiting without it`); a reap wait that overruns is not an error |
| `serve`, during startup (configuration, Redis connection, membership bootstrap, binding) | startup is abandoned, not drained -- nothing is serving yet -- and `serve` exits **`130`** with `tunnel-relay: SIGTERM received during startup; serve stopped before any listener was serving`. Nothing is left bound. Blocking work already handed to the runtime (the membership state store open) is given at most the 5 s runtime-shutdown bound after the diagnostic, then abandoned with the process; every such write goes through a temporary file and one rename, so what an abandoned write can leave is a `.tmp-*` file, not a torn state file |
| `serve`, serving | orderly drain: `tunnel-relay stopping: signal=SIGTERM` on stderr, then `RunningRelay::shutdown` (bounded), and for a cluster the peer listener set draining, the peer refresh task and the membership runtime joined; then `tunnel-relay stopped: signal=SIGTERM` and exit **`0`** |
| `tunnel-relay` finite commands that **write** -- `initialize`, `activate-first-incarnation`, `provision-catalog`, the day-2 catalog commands (`add-user`, `add-device`, `add-service`, `set-grant`, `revoke-grant`, `revoke-device`, `revoke-credential`; M6-C31), `recovery-initialize`, `recover` | a first stop request is acknowledged on stderr (`... received during provision-catalog; letting it finish, because an interrupted write cannot be undone`) and the command runs to its own bounded outcome, which is printed and sets the exit status as usual; a second abandons it with **`130`** and says the outcome is unknown. Each catalog write is one Redis script, so an abandoned one is complete or untouched and its rerun says which (M6-C35); an approval consumed part-way cannot be re-used, so finishing is the only stop that leaves a known state. Read-only commands (`check-config`, `check-serve-config`, `recovery-observe`) keep the default action; there is nothing for a stop to damage |
| either, a **second** stop request during **any** wait on the stop path | exits **`130`** at once, without waiting. For `connect` that is every wait: the pre-ready unwind, the drain join, the MCP reap wait and the join of a connector whose session closed by itself -- all go through one helper whose first arm is the next stop request, so none can be missed -- with `... received during the orderly stop SIGTERM began, while waiting for <what>; exiting without waiting` (or `... received while waiting for <what>` when no stop began it). For `serve` it is the serving drain; for the writing commands, the finish. A service manager's own escalation (systemd's `TimeoutStopSec`, then SIGKILL) is unaffected |

**Every wait on the stop path is bounded, and what each bound abandons.** `connect`: the pre-ready unwind 2 s (the attempt is then dropped, closing its sockets); the drain join `handshake_timeout + overlap` (the connector is dropped unjoined and the process exits `130`); the reap wait 5 s (the process exits and a sentinel, if installed, fires); a closed session's join the same drain bound (exit `1` `SUPERVISOR_FAILED`). Both binaries: after the command has returned, **at most 5 s** for work still on the runtime's blocking pool, then the process exits and that work is abandoned (`Runtime::shutdown_timeout`; before this a `serve` whose startup was stopped while a `spawn_blocking` open of its membership state sat on a hung mount would print its `130` diagnostic and never exit, because dropping a runtime waits for blocking tasks indefinitely). A state write abandoned that way leaves its temporary file, not a torn state file: the state stores write then rename. **Not bounded, by design:** `serve`'s serving drain joins the membership runtime without a deadline (`MembershipRuntimeHandle::shutdown` documents why a wall-clock abort would detach a store write), so there the escape is a second stop request or the service manager's SIGKILL; and a first stop request lets a writing relay command finish, which each command's own 2 s Redis and recovery-phase timeouts bound.

**A `stopped` event can follow no `ready` event.** When the connect attempt completes during the pre-ready unwind -- before it observed the cancellation -- the session was ready and is stopped in order, but the stop request arrived first, so the session loop that prints `ready` never ran: the stream is the `stopped` event alone, exit `0`. A consumer should key on `stopped`, not on a `ready`/`stopped` pair.

**Why a live stop exits `0` and not `130`.** An orderly stop that completed is the documented meaning of `0` for `connect`, the M7 gates that retire a CLI through SIGINT require `0`, and systemd records an exit `0` after its own SIGTERM as a clean stop, whereas `130` would need `SuccessExitStatus=130` in every unit. `130` keeps its meaning: interrupted *before* an orderly completion could be recorded. A unit for `serve` or `connect` should still list `SuccessExitStatus=130` if it stops the service while it may be starting.

**Inherited `SIG_IGN` is overridden, on purpose.** Installing a handler replaces the disposition a process inherited, so a `connect` or `serve` started as a background job of a non-interactive shell -- which starts it with SIGINT ignored -- or under `trap '' TERM` now stops on those signals too. This was chosen over honouring the inherited disposition for three reasons. (1) It is the defect M6-C27 recorded: an operator's stop request silently ignored for ten seconds and then reported as `DEADLINE_EXCEEDED`. (2) Service managers do not depend on it: systemd documents that it resets signal dispositions to their defaults for the processes it starts (with SIGPIPE ignored by default, `IgnoreSIGPIPE=`), so the inherited-ignore case arises from shells and wrappers, where whoever sent SIGINT or SIGTERM meant it; launchd's behaviour was not checked here. (3) Honouring it portably would need the current disposition read with `sigaction`, which `tokio`'s signal API does not expose and which needs `unsafe` (the client library is `#![forbid(unsafe_code)]` and the relay library `#![deny(unsafe_code)]`; neither `main.rs` carries the attribute, so this is the repository's rule rather than a compiler-enforced one there). On Linux alone `SigIgn` in `/proc/self/status` is readable without `unsafe`, but not on macOS, the only host this has run on. `tokio` installs its handler over an inherited `SIG_IGN` (`signal-hook-registry` calls `sigaction` unconditionally; measured: the inherited-ignored tests below exit `130`). A `connect` that must survive a terminal's Ctrl-C belongs in its own session (`setsid`) or under a service manager, not behind an inherited disposition. **SIGHUP is not handled**, so `nohup` keeps working and a hangup still takes the default action. Windows builds handle Ctrl-C only.

**What is measured, and what is not.** Measured by process-level tests that hold the real binary in the phase with a peer that accepts and never answers, witness the phase from that peer, and assert the status, the diagnostic and that the exit followed the signal promptly: `connect` during the TLS handshake and during the WebSocket upgrade, SIGTERM and SIGINT, default and inherited-ignored dispositions (`crates/tunnel-client/tests/signal_shutdown_cli.rs`); `serve` during the Redis TLS handshake (both signals, and SIGTERM inherited as ignored) and during the membership bootstrap's checkpoint request, and `activate-first-incarnation` held in its Redis TLS handshake with one stop request and with two (`crates/tunnel-relay/tests/m7_startup.rs`); `serve` serving, one-node cluster over a TLS Redis forwarder, SIGINT and SIGTERM (`m7_deployment_process.rs`, run explicitly with `TEST_REDIS_URL`); `connect` with a live session stopped by SIGTERM (the M1 harness's CLI smoke). **Measured below the process level only:** the second-stop and bound logic of the `connect` waits -- a second stop request ends the reap wait and a hung drain join at once, and a hung join ends within its bound -- by unit tests that drive the waits with a synthetic stop request (`a_second_stop_during_the_reap_wait_exits_cancelled_promptly`, `a_second_stop_during_a_hung_join_exits_cancelled_promptly`, `a_stop_whose_join_hangs_exits_cancelled_within_the_bound` in `crates/tunnel-client/src/main.rs`); that `run_connect` routes its waits through them is read from source, not tested, because reaching them in a real process needs a relay (and, for the reap, a live MCP session). **Not measured:** the HELLO/WELCOME, owner-fence, data-socket and DATA_READY sub-phases one by one (they observe the same cancellation token); the ready-boundary race (the `biased` select is source-held; no test lands a signal in the same poll as the attempt's completion); a second signal during `connect`'s live drain or `serve`'s serving drain at the process level; `serve`'s binding phase; a non-cluster `serve` while serving; a writing relay command stopped while its writes are in flight (the test holds `activate-first-incarnation` in its Redis handshake, before any write, and `provision-catalog`'s record writes are not held); the 5 s runtime-shutdown bound firing on a hung blocking task (no hung open could be produced: a FIFO as the membership state file is refused by the store's regular-file check before it is opened, and nothing else here blocks on demand); any Windows build. **A stop during a data rotation is measured since M6-06:** `scripts/m6-shutdown-phases-verify.sh` pins the client's and the relay's phase with the `test-hooks` client build, witnesses it (`status --json`; `tunnel_relay_sessions_by_rotation_phase`) and sends SIGTERM to each in active, preparing, quiescing, draining, committing, aborting and (since the M6-06 review) retiring. Each exits `0` in about 7--17 ms, leaves an empty process group, releases the owner slot, and gives the echo in flight an explicit outcome (task rows M6-C135, M6-C132). **Recovering is not measured (task row M6-C136):** no hold reaches it. Holding the drain until the 10 s overlap deadline made the relay end the whole session (`control read failed` on the client) rather than enter retained recovery, which the protocol permits ("enter retained-state recovery ... or fail"). Reaching recovering needs a lost data socket, meaning a proxy that cuts it. **Residual window:** a signal delivered between `exec` and the handler installation still takes the inherited disposition. Measured on a **release** build of `connect` at `da93db6` (SIGTERM sent a fixed delay after Python's `Popen` returned, 20 trials per delay, binary pre-warmed, load average about 10; log nonce `m6c23-window-release-20260923T044427Z-39379`): at 0 and 1 ms all 40 died by the signal, at 2 to 8 ms all 120 exited `130`, so the window is about 1--2 ms from spawn on this host. The M6-C23 review measured about 4--5 ms on a **debug** build (at most 3 ms 60/60 died, 4 ms 27/40, 5 ms 2/20, from 6 ms 0/100). And the first run of the relay tests on macOS signalled a freshly linked binary 800 ms after spawning it and killed it before `main` had armed anything -- the first exec of a new executable can be held by the system's scan -- which is why the tests now witness the phase instead of sleeping.

### Reconnecting `connect`

**Implemented (M6-C23).** Before this, `connect` exited `4` the moment its relay was unreachable or its session ended, so a device dropped off for good on any network change, relay restart or laptop sleep. It now runs a loop: one connect attempt and, if it becomes ready, its session; when that ends by itself, classify the cause, and either exit with it or wait and try again. A stop request ends the loop in every phase (previous section).

**Which causes are retried.** `Cause::reconnect_class` in `crates/tunnel-client/src/main.rs` decides, with an exhaustive match and **no fallback arm**, like `Cause::exit_code`: a new cause does not compile until someone states whether a retry could ever help. Each arm is justified from the code that produces the cause:

| Cause (exit) | Class | Why, from the producer |
| --- | --- | --- |
| `INVALID_INVOCATION`, `CONFIG_ERROR`, `INVALID_CONFIG` (2) | terminal | local input; the profile is read once and a retry reads the same bytes |
| `CREDENTIAL_ERROR` (3) | terminal | the local credential could not be loaded (`load_client_config`); TLS certificate verification refused a certificate for a reason other than time (`ClientError::TlsRefused`, below); or the relay refused this device's certificate as not current and it is past `notAfter` on this host's clock too. None changes by waiting |
| `TRANSPORT_ERROR` (4) | retryable | refused TCP, a reset, EOF, a closed control or data socket, a failed data rotation or exhausted retained recovery: what a relay restart, a network change or a laptop waking produces. Also, since M6-C105, a `STREAM_FORGET` whose proof was consistent but still waiting for the relay's final data-channel ACK when its 5 s revalidation window closed (`STREAM_FORGET terminal proof did not converge before its deadline`): a stalled or lossy device produces exactly that, and the connector cannot tell it from a relay that never sent the ACK |
| `SESSION_CLOSED` (4) | retryable | the connector's session ended with `Readiness::Closed` and a clean join: the relay or the path ended it, not a local fault. (A relay stopped in order was measured to surface as `TRANSPORT_ERROR` instead; both are retried) |
| `DEADLINE_EXCEEDED` (5) | retryable | the 10 s TLS/WebSocket/HELLO deadline: a blackholed route or a relay too busy to answer |
| `AUTHORIZATION_STALE` (4) | retryable | **not a revoked credential.** It is produced only when one stream's operation-authorization deadline lapsed with a frame already queued (`lib.rs`, the data writer and `dispatch_fin`), and the session is failed so the queued side effect cannot be replayed; a fresh session starts with no streams and fresh authorizations. Exit `4` since M6-C39 (owner decision, 2026-09-25); it was `3`, whose "re-enroll or re-authorize" advice sent the operator to the wrong fix |
| `RESOURCE_EXHAUSTED` (7) | retryable | a per-session local budget (queue, OPEN retention); the library documents that the caller must start a fresh session |
| `OWNER_BUSY` (7) | conditional | retried only within **60 s** of this process's own ready session ending, as that session's stale owner lease; terminal otherwise -- see below |
| `CANCELLED` (130) | terminal | this process's own stop path |
| `SUPERVISOR_ABSENT` (8), `SUPERVISOR_RUNNING` and `SUPERVISOR_LOCK_FAILED` (9), `IPC_UNAUTHORIZED` (3) | terminal | supervisor IPC causes (M6-06): the profile lock refuses before the first attempt (`9`, or `3` for a lock it cannot trust), and `SUPERVISOR_ABSENT` comes only from `status`; none is produced by a session |
| `PROTOCOL_ERROR`, `SUPERVISOR_FAILED`, `SIGNAL_ERROR` (1) | terminal | a version skew or a violation (TLS rules out corruption), a panicked supervisor, a broken signal subsystem: a retry repeats each. A violation is evidence the peer sent that contradicts the protocol, never evidence that did not arrive in time: before M6-C105 an expired `STREAM_FORGET` proof was reported here, and a `connect` stopped for 40 s with an echo in flight exited `1` in 1 of 5 live runs instead of reconnecting |

**The TLS line, drawn narrowly.** Every handshake failure used to be one opaque `websocket handshake failed` -- `sanitize_error` erases the backend error -- so a wrong `server_ca` was indistinguishable from a relay that is still restarting. `tls_refusal` in `crates/tunnel-client/src/lib.rs` now classifies **by rustls variant, before sanitization**, into three outcomes. **Terminal** (`ClientError::TlsRefused`, `CREDENTIAL_ERROR`, exit `3`): this client refusing the relay's certificate as from an unknown issuer, badly signed, revoked, not valid for the host or not for server authentication; and the relay refusing this device's certificate with an unknown-CA, bad, unsupported, revoked, unknown or required-but-absent certificate alert -- properties of the identities, which no retry changes. **Retryable, with the reason** (`TRANSPORT_ERROR`): a certificate that is valid except for the **time**, because clock skew between a CA, a relay and a device is ordinary. On the relay's certificate, `Expired` or `NotValidYet` on this host's clock is retried with a message saying the relay's certificate needs renewing or this host's clock is wrong. On the device's certificate the relay sends `certificate_expired`, which rustls 0.23 sends for an expired **and** a not-yet-valid certificate alike (`impl From<CertificateError> for AlertDescription`), judged on the relay's clock; so `connect` reads **its own certificate against its own clock** (`attempt_error` in `main.rs`, the chain-wide window `doctor` uses): past `notAfter` here too is terminal `CREDENTIAL_ERROR` naming the expiry time; not yet valid here, or valid here, is retried with a message naming clock skew, and is accepted on a later attempt once valid. **Opaque and retryable** (`TRANSPORT_ERROR`): a reset, an EOF, an I/O error, a timeout, an unclassified alert (`handshake_failure`, `decrypt_error`, `access_denied`), certificate errors outside the lists. **A host whose clock is badly wrong** -- a dead real-time clock booting at 1970, say -- finds every certificate not yet valid: the relay's (retried, with a message naming this host's clock) and its own (the relay's `certificate_expired` alert, read here as not yet valid, retried and naming the issuer's clock). Nothing is terminal, so the device retries visibly and connects once the clock is set; it is not measured with a 1970 clock, only with a certificate 20 s ahead. Every reason is fixed text written in the crate; nothing from the peer or its certificate is carried. **Measured:** against a real `serve`, a device certificate re-issued with `notBefore` 20 s ahead drew `certificate_expired`, was retried, and connected once valid; one past `notAfter` exited `3` with no backoff (`m6_reconnect_process.rs`); the local stand-ins in `reconnect_cli.rs` hold every other line.

**A refusal after TLS.** A device whose catalog credential is revoked, expired or unknown, or whose `device_id` does not match its certificate, passes TLS and is refused at HELLO. On a single relay that refusal now closes the control socket with `1008` `DEVICE_IDENTITY_REJECTED` (M6-C32), which the client reports as `CREDENTIAL_ERROR`, so this loop exits `3` without a retry -- measured with reconnect on (`m6c23_an_identity_mismatch_exits_three_without_retrying` in `m6_reconnect_process.rs`, and M6-C32's own identity cases in `m6_provisioning_process.rs`, which now run with the default policy and assert no `backoff` event). A catalog credential whose `not_before` is still ahead is clock skew and stays a retryable `TRANSPORT_ERROR` (M6-C32's review), so it is retried until valid. **The protocol-major refusal is typed too (M6-C38):** the relay closes a HELLO naming another major `1002 PROTOCOL_UNSUPPORTED` (`RelayError::UnsupportedProtocolMajor`), and the client reports it as a terminal `PROTOCOL_ERROR`, exit `1` -- measured against the real `serve` with a raw device socket (`m6c38_a_hello_on_another_protocol_major_is_closed_typed`) and with the real client against a stand-in relay (`a_protocol_major_refusal_exits_protocol_error_without_retrying` in `reconnect_cli.rs`). On a **cluster** relay an unknown key now draws the same `1008` close at the ingress, and an owner answers a forwarded registration's refusal with a status the ingress turns back into the owner-local close (`409` owner busy, `401` identity, `426` protocol major; `503` for a refusal that may heal, which stays an untyped, retried close) -- unit-tested, not yet run in the production-cluster gate (M6-C43). **These statuses are mixed-version safe** (rolling or mixed-version upgrades are otherwise not supported in this alpha; operator.md, "What the alpha can and cannot do today"): an owner from before M6-C38 answers `403` for every refusal except owner busy, a catalog outage included, so the ingress keeps `403` an untyped, retried close and never makes it terminal; while such an owner remains, its genuine identity refusals are retried as they were before. **A loop over a refusal that is still untyped is visible, not silent:** every failure prints a `disconnected` and a `backoff` event with the cause's code and message (one stderr line without `--json`), and `attempt` counts the consecutive failures; at the 60 s cap a device makes one attempt every 30--60 s. It is **bounded only by `reconnect.max_attempts`**, which is unlimited by default because a laptop offline for hours must still come back; an operator who wants such a refusal to surface as an exit sets it.

**`OWNER_BUSY` and the stale lease -- measured.** When a relay dies without releasing it, the device's owner record stays in Redis until its lease lapses (`owner_lease`, 6--30 s, default 30 s from the last renewal), and every reconnect until then is refused `OWNER_BUSY`. Measured on the real binaries in four runs, the last on the merged tip `55de8b1` (log nonce `m6c23r-reconnect-20260923T083210Z-2522`; M6-C23 lists the others): after `serve` was **SIGKILLed** and restarted, the client reconnected 29.8--30.4 s after the new relay was listening, refused `OWNER_BUSY` until then; after an orderly **SIGTERM** stop, which releases the owner, it reconnected in 499--866 ms. (The gate runs a short policy, 200 ms to 1 s, and was refused 38 to 40 times; the count depends on the policy, the 30 s does not. Under the default policy the retries in those 30 s are about five -- derived from the backoff, not measured -- and the reconnect lands at the first attempt after the lease lapses, which the growing delay can put well past 30 s.) M6-C40 records the outage as a design question. So `OWNER_BUSY` is retried while it can be this process's own previous session -- within `OWNER_BUSY_RECONNECT_WINDOW` (60 s, twice the maximum lease) after that session ended -- and is terminal on a fresh process's first attempt, where there is no previous session: a second connector for the same device still exits `7` at once. The only witness of that first-attempt rule with reconnect on is the unit test `owner_busy_is_retried_only_within_the_window_after_our_own_session`; the M7 ownership gates spawn the binary with `--no-reconnect` and never reach the loop.

**A relay whose device's path vanished lets go within a stated bound (M6-C68).** Before M6-C68, when the device's side of the path vanished while the relay stayed up -- a laptop waking on a new network, a NAT rebinding, a VPN dropping -- the relay kept the old session forever: it sent no pings, its control loop read without a timeout, and the stale session kept renewing its owner lease, so `register_control` answered `OwnerBusy` for every reconnect. The M6-C23 review measured it by cutting the client's side of both sockets behind a proxy that held the relay's side open: **78 `OWNER_BUSY` refusals and exit `7` at 60.7 s**, no second `ready`. The owner-local control task now sends a WebSocket Ping every `DEVICE_CONTROL_PING_INTERVAL` (10 s) and ends the session once no inbound frame of any kind has arrived for `DEVICE_CONTROL_IDLE_TIMEOUT` (30 s); a write does not count, since it completes into the kernel's buffer on a dead path. The exit is the ordinary control-task exit, so the session and its owner slot are released exactly as on a device's own close, and the closure is recorded with cause `liveness_timeout`. Both constants live in `tunnel-protocol` with compile-time bounds, and this client asserts that `OWNER_BUSY_RECONNECT_WINDOW` outlasts the relay's eviction. Measured on the real binaries with the reviewer's cut path (`m6c68_a_relay_evicts_a_device_whose_path_vanished_and_admits_its_reconnect`, run by `scripts/m6-reconnect-verify.sh`; tasks.md M6-C68 has the runs): the client was refused `OWNER_BUSY` about 40 times under the gate's short policy and reconnected about 30.3 s after the cut; a healthy session left idle for 40 s first was not evicted. Under the default policy the reconnect lands at the first attempt after the eviction, which the growing delay can put later than 30 s, still inside the 60 s window since the last refusal precedes the eviction. Not covered: a device attached through a non-owner cluster relay, whose forwarding loop has no deadline yet (M6-C68 records it). The client unit in `examples/service/` stays set so that a relay which does not let go stays visible and recovers by itself (operator.md section 4).

**Backoff.** The delay before the *n*-th consecutive retry is uniform in `[c/2, c]` with `c = min(initial_delay_ms * 2^(n-1), max_delay_ms)` -- "equal jitter". Defaults: `initial_delay_ms = 1000`, `max_delay_ms = 60000`, `max_attempts = 0` (no limit); validation allows 100 ms to 300 s. Why these:

* **The floor** (`c/2`, and `initial_delay_ms >= 100`) keeps a relay that refuses at once from turning the loop into a busy loop.
* **The jitter** spreads devices that lost the same relay at the same instant -- a relay restart -- over half of each ceiling, so they do not arrive together; it is drawn from the operating system's generator (`uuid` v4), independent per device. Full jitter (`[0, c]`) spreads further but allows a near-zero delay; equal jitter was chosen for the floor.
* **The cap** (60 s) bounds how long a device stays away after its relay is back: at most one capped delay plus a handshake. The ceiling reaches it on the 7th consecutive failure (1, 2, 4, 8, 16, 32, 60 s), about two minutes in.
* **The reset rule.** The consecutive-failure count returns to zero only after a session that stayed ready for `max_delay_ms`; a session that ends sooner counts as a failure, so a relay that accepts and drops at once still backs off instead of being retried at the first delay forever.
* **The limit** (`max_attempts`) is there for an operator whose supervisor should see a failure after a while; it counts consecutive failures and exits with the last cause's own status.

**Turning it off.** `--no-reconnect` for one run, or `[reconnect] enabled = false` in the profile: the first end of session is the exit, exactly as before M6-C23, for a supervisor that prefers to own restarts.

**Events.** Under `--json`, besides `ready`, `connect-status` and `stopped`, the loop prints `ok:true` events with `result.state`:

| `state` | When | Fields |
| --- | --- | --- |
| `disconnected` | an attempt or a session ended with a retryable cause | `attempt` (the retry about to be made), `sessions` (sessions that became ready so far), `session_id` and `ready_ms` (only if a ready session ended), `code`, `message` |
| `backoff` | immediately after, before the wait | `attempt`, `sessions`, `code`, `delay_ms` |
| `reconnecting` | the wait ended; the attempt starts | `attempt`, `sessions` |
| `reconnected` | an attempt that followed a failure became ready; the usual `ready` event follows | `attempt`, `sessions`, `session_id` |
| `children_unreaped` | the 5 s wait for supervised MCP children to be reaped after a session ended ran out; the process goes on (to exit, or to back off) and the sentinel, if installed, ends them | `unreaped` (the count still running), `bound_ms` |

They carry identifiers, counters, durations and the cause's code and bounded message -- the same message a terminal error event carries -- and never payloads, adapter arguments, typed text or certificate material. Without `--json`, `disconnected` and `backoff` are one line on stderr. A consumer should expect more than one `ready` event per process, each with a new `session_id`.

**Refusals the connector sent (M7-C167).** Every `connect-status` event carries `open_refusals_sent`, an object with exactly one key per fixed refusal code in `tunnel_protocol::open_refusal::CODES` -- `GOAWAY`, `RESOURCE_EXHAUSTED`, `EXPORT_DENIED`, `OPERATION_DENIED`, `STREAM_EXISTS`, `STALE_REQUEST`, `AUTHORIZATION_EXPIRED`, `CANCELLED` -- each the number of OPEN `REJECTED`s this session has sent with that code, zeros included, so the keys never vary. It is a counter only: no reason text, category, stream ID or operation ID. **It counts refusal frames queued, not distinct requests.** A journaled refusal is counted when it is queued, and a retried OPEN answered from the OPEN journal with the same stored refusal is not counted again. The three refusals sent without journaling (`STREAM_EXISTS` "stream ID was already forgotten", `RESOURCE_EXHAUSTED` "OPEN idempotency retention is full" and `STALE_REQUEST` "OPEN was already forgotten") are counted again on every retry of the same OPEN. A count also means queued, not delivered: a refusal placed in the critical control spill is counted even if the session then ends before it is written. The counts belong to the session: they start at zero for every session, a reconnect included (compare `session_id`), and saturate rather than wrap. **Rate bound:** a change to any other `connect-status` field prints an event at once, carrying the current counts. A change to `open_refusals_sent` alone prints at most one event per second (`REFUSAL_STATUS_INTERVAL`), and a count held back by that bound is printed in a trailing event when the second ends. So a storm of refused OPENs prints about one event per second, not one per refusal. When the session ends, whether by a stop request, a readiness close such as a relay GOAWAY, or a stopped channel, the latest status is read once more, and printed if it holds a count or field not yet printed, so the final counts are never lost to the bound. This is the device-side record of what the relay reports as `503 DEVICE_REJECTED` (or `RESOURCE_EXHAUSTED`, or `ROTATION_FREEZE` for a unary echo refused `GOAWAY` during a frozen rotation attempt, M6-C204); the relay's own `connector_rejected` line is in [operator.md](operator.md) (Refusals). Only the M2 connector publishes status, so an explicit M1 profile reports none. The supervisor IPC `status` snapshot carries the same counts ([Supervisor status IPC](#supervisor-status-ipc), M7-C168).

**Rotation, children and exports across a reconnect.** A reconnect is a **new session**: new session id, owner epoch and generation; there is no resumption of the old one, and in-flight operations on it end with their stream (a mutation's outcome is then unknown -- see [protocol.md](protocol.md)). Rotation state belongs to the session and starts afresh. **Supervised MCP and ACP children are restarted, not kept:** the handler registry is built per attempt and dropped with the connector when the session ends, which ends every MCP/ACP protocol session and kills each child's process group (MCP's kill is requested on drop and the loop waits, bounded at 5 s, for the reap before backing off -- M6-C29, and M6-C28's residual gap is unchanged); ACP's drop kills synchronously. Kept children would outlive the device session whose consumer requests started them, which the M3-04 rule forbids, and their protocol sessions could not be resumed through a new relay session anyway; a consumer re-initializes, exactly as after a process restart. A Streamable HTTP MCP export re-reads its bearer token file on each attempt. The profile itself is **not** re-read; configuration changes still need a restart.

**Tested on the real binaries.** `crates/tunnel-client/tests/reconnect_cli.rs` (ordinary workspace suite, local stand-ins for the relay): a refused relay backs off with each delay inside its `[c/2, c]` window and gives up at `max_attempts`; two devices failing together draw different delays; a relay that **resets** or **closes** the connection mid-handshake is retried; a relay certificate from an untrusted CA, and a relay refusing the device certificate with a TLS alert, exit `3` after exactly one connection and no backoff; SIGTERM and SIGINT during the backoff exit `130` within 1 s; `--no-reconnect` and `enabled = false` exit on the first failure. `crates/tunnel-relay/tests/m6_reconnect_process.rs` (real Redis, `scripts/m6-reconnect-verify.sh`): `serve` SIGKILLed mid-session and restarted, then stopped with SIGTERM and restarted -- the client reconnects to a new session each time and an echo through the relay succeeds after each; a `connect` started before its relay backs off until `serve` appears; and a device certificate from a rogue CA and a profile whose `server_ca` did not sign the relay each exit `3` after one attempt (M6-C54's issuer cases, re-measured). Each is held red by a defeat of its own mechanism in `scripts/m0-guard-exit-codes.py` or, for the Redis gates, by hand (M6-C23 records both). **Not measured:** a network partition or a laptop sleep as such (the reset, EOF, refused-TCP and relay-death cases are their observable ends); a refusal at HELLO (M6-C38); a reconnect with a live MCP or ACP child (the per-session registry is source-held); a relay cluster; any Windows build.

### Relay configuration dry run

`tunnel-relay check-serve-config --config PATH` is implemented. It is the read-only dry run for the `ServeConfig` that `tunnel-relay serve --config PATH` constructs: it applies every rule `serve` applies to the configuration document, including the authoritative Redis namespace rule the catalog owns, the Redis TLS-material and `rediss://` scheme pairing, rotation timing, and the cluster and recovery cross-field rules.

The command is inert and deterministic. It reads the one configuration file named on the command line and nothing else; it binds no listener, makes no Redis or peer connection, reads no credential, private key or JWKS material, and creates or modifies no file. It is therefore safe to run against a production configuration, and it returns the same verdict on a checkout whose placeholder credential paths do not exist. Validating the referenced material remains `serve`'s own startup work: a successful dry run is evidence about the configuration document, not about the deployment's files.

It takes no flag other than `--config PATH`. A dry run that could select a different authority file, namespace or trust path than `serve` would prove nothing about the deployment, so no override exists.

Exit codes follow the relay's implemented bootstrap behavior: `0` when the configuration is valid, `1` with a redacted field-level reason on stderr when it is not or when the file cannot be read. The client exit-code table above is not wired into the relay; that change waits for relay CLI parsing and its compatibility tests. The relay's legacy `check-config [PATH]` stays a `tunnel_core::RelayConfig` check and is not evidence for a serving document.

`--json` emits versioned JSON on stdout and logs on stderr. Finite commands emit one result object; `connect --json` emits newline-delimited lifecycle events. Each result contains `schema_version`, `command`, `ok`, and either `result` or `error { code, message, retryable, operation_id? }`. Never interleave human progress text with JSON. `retryable` permits retrying safe admission/connection work, not replaying an ambiguous mutation.

## State ownership and crate boundaries

Use a single actor per device ownership epoch. That actor owns control/data attachment state, current and candidate generation, unique physical connection IDs, ticket consumption, per-direction/per-stream sequence allocation, drain watermarks, stream accounting, and shutdown. Socket reader tasks send typed events; bounded writer tasks perform I/O from actor-selected effects. No HTTP handler directly mutates rotation state, and no mutex guard is held across an I/O await.

Data handover follows the authoritative drain rules in [protocol.md](protocol.md): quiesce new payload assignment to the old socket, record each direction/stream's final old-generation sequence, wait for acknowledgment through those watermarks, commit the candidate, and retire the drained old socket. A payload queued while draining remains bounded and is sent on the selected new generation after commit. The default 30-second overlap budget still includes candidate handshake and drain; pending work cannot extend it. Frame sequence identity belongs to a stream direction for its retained session and never resets on socket rotation.

The retained M2 carrier-recovery path keeps the same authenticated control actor and logical session. Its first recovery candidate is eligible after the closure barrier; later failed candidates use the shared 100 ms and 200 ms gaps, with at most three physical attempts under one immutable episode deadline. Each `RECOVERY_CLOSED` list is a per-attempt delta; prior IDs remain in fenced recovery history and are not repeated on the next wire exchange. A failed final attempt is terminal. This path does not implement whole-session control reconnect, process-restart recovery, owner migration, or resume after retention expiry; those boundaries require fresh sessions and explicit operation uncertainty.

Keep transition logic synchronous and deterministic: `(state, event, monotonic_time) -> (next_state, effects)`. Name typed state variants after the authoritative protocol state table, including explicit quiescence, draining, commit, and retirement phases; a generic `connected: bool` cannot represent them. Effects such as opening a candidate, dispatching an adapter request, persisting ownership, and setting deadlines are explicit. Clock, randomness, credential lookup, and network boundaries are injected for tests.

Every queue has a count and byte limit; a full queue returns a typed overload or pauses admission. Charge candidate traffic to the existing session budget. The per-device session byte budget carves out `131,072` bytes (four 32 KiB control messages) that only control-lane charges may use: data-lane charges are refused above `max_queue_bytes - 131,072`, control-lane charges only at `max_queue_bytes`, and the session snapshot reports `control_reserved_bytes`, `data_bytes_limit` and `data_bytes_high_water` beside `queue_bytes_limit` (see [protocol.md](protocol.md)). Fair scheduling, cancellation, slow adapters, peer forwarding, and replay share explicit resource budgets. Do not add unbounded channels, detached retries, or background tasks whose owner/shutdown path is unclear.

Public consumer admission uses two layered permit bounds, not one. `max_pending_operations` (default 64, validated 1..=64) is the relay-global process bound; it is reserved before a request body is read and is deliberately not tenant-scoped. `max_pending_operations_per_owner` (default 48, validated 1..=64) bounds the permits one `(tenant_id, device_id)` owner scope may hold at once and is reserved only after the authenticated catalog identity fixes that scope. The effective per-owner bound is `min(max_pending_operations_per_owner, max_pending_operations)`, because the global permit is always reserved first. The relay-global permit is held for the whole operation round trip, including the lifetime of a public stream, so without the per-owner bound one tenant's in-flight operations refuse every other tenant's public request with the typed `ADMISSION_LIMIT` outcome. The default leaves at least a quarter of relay ingress capacity unreachable by any single tenant/device while keeping one owner enough headroom for its `max_streams_per_device` allowance spread across a cluster's non-owner ingress relays; deployments serving many concurrent tenants should lower it. Both bounds refuse with the same typed `ADMISSION_LIMIT` / `not_dispatched` outcome and a bounded retry hint; neither adds a new refusal code. Each permit is released exactly once on drop, so an abandoned request, a refused peer admission, a cancelled upgrade and a normal close all return capacity. A per-scope entry exists only while it holds at least one permit, so the registry is bounded by the relay-global permit count rather than by the catalog. Scope-level rate limits for principals and connector counts remain the separate planned limits in [protocol.md](protocol.md); the catalog-read routes (`/v1/devices`, `/v1/devices/{device}/services`) take only the relay-global permit because they hold it for one bounded catalog read and never across a device round trip.

Supervise tasks in owned groups; a reader/writer panic or unexpected exit becomes an actor event and fails the affected scope. Shutdown first stops admission, then requests adapter-specific cancellation/drain, records terminal or unknown outcomes, closes data/control, and joins tasks within a deadline. Avoid global mutable registries except bounded routing indexes whose entries point to actor handles.

| Boundary | Responsibility |
| --- | --- |
| `tunnel-core` | IDs, configuration, policy values, typed domain errors |
| `tunnel-protocol` | Codec, limits, pure state transitions and model fixtures |
| `tunnel-identity` (future) | TLS identity extraction, trust/credential contracts; no business routing |
| `tunnel-relay` | Axum listeners, authentication middleware, request admission, actor supervision |
| `tunnel-cluster` (future) | Private HTTP/3 adapter, approved peer directory and fenced owner routing |
| `tunnel-client` | CLI, local credential store, device lifecycle, export supervision and IPC |
| `tunnel-vfs`, `tunnel-mcp`, `tunnel-cua`, `tunnel-acp` (future) | Typed adapter operations with independent local policy and failure semantics |

Create crates at their implementation milestone; keep narrowly used helpers as modules until separation improves ownership or testing. Domain services accept typed authenticated principals and bounded request objects, not Axum request bodies or raw headers. Use typed errors in libraries and contextual cause chains at binary boundaries; a single error conversion table maps them to HTTP, WebSocket, peer, and CLI responses.

Initial cluster operation uses the deliberately constrained authority profile in [cluster.md](cluster.md): several relays, one authoritative Redis primary over an authenticated `rediss://` connection, separate durable-catalog and ephemeral-coordination namespaces, no automatic Redis failover, and explicit quiescence plus a newly supplied externally approved incarnation after authority loss, restart or restore. Durable catalog records survive an incarnation change; leases, presence and tickets do not. AOF/fsync and verified backups are durability choices, not consensus or promotion authority. A missing, ambiguous or unverified Redis authority makes the service unready and stops admission. This trades automatic failover for a failure model that can be tested and explained. It does not claim a highly available coordination layer.

## Implemented local doctor

`tunnel-client doctor --config PATH [--json]` reads the local profile and credential files, checks certificate/key match, Unix private-key and parent-directory permissions, and client/server-CA certificate validity. It opens no network connection and invokes no export. Relative credential paths resolve from the profile directory.

Exit 0 means those local checks passed; exit 2 means invalid invocation/configuration; exit 3 means a credential, permission or expiry failure. JSON uses schema version 1 and omits paths and credential contents. Since M6-06 `supervisor_ipc` reads the running supervisor through the same local IPC `status` uses and reports `ok`/`SUPERVISOR_IPC_OK`, `not_running`/`SUPERVISOR_ABSENT`, `failed` with the IPC's closed code (`IPC_UNAUTHORIZED`, `IPC_TIMEOUT`, ...), or `not_run`/`SUPERVISOR_IPC_NOT_RUN` when the configuration cannot name the socket; like `process_containment` it never changes `ok` or the exit status, because `doctor` is also run before the first `connect`. Before M6-06 it reported `SUPERVISOR_IPC_NOT_IMPLEMENTED`. Since M0-07 `renewal` reports `none`/`RENEWAL_NONE`, `pending`/`RENEWAL_PENDING` with `pending_since_unix` (when the pending key was written, so a stale one is visible), or `interrupted`/`RENEWAL_INTERRUPTED` for a swap killed between its two renames (the key-match check fails meanwhile, and the next `connect` or `credentials renew` resolves it); `doctor` changes nothing to find it, and the check never changes `ok` or the exit status.

**`result` is always present, including on a failing run** (M6-C07). Every check reports its own status, and `not_run` is a distinct status from `failed`, so a report says which checks were attempted rather than leaving a reader to infer it from the report's absence. This matters most where it used to be worst: `supervisor_ipc` and `process_containment` describe the host rather than the configuration, are computed before the configuration is even read, and an unprovisioned machine — where every run fails — is exactly the population that needs to read them. Emitting the result alongside an error leaks nothing: every leaf of the report is a fixed status or code string, a permission mode, a certificate count or a unix timestamp. `--network` is rejected because that mode is not implemented. Non-Unix permission validation reports unsupported rather than claiming a pass.

Current macOS evidence is 39 library tests, 8 binary unit tests, 5 actual CLI fixtures and strict client all-targets Clippy; see [the continuation evidence](m7-verification.md). This does not verify the broader IPC/status/diagnostic-bundle contract below.

## Supervisor status IPC

**Implemented (M6-06).** `tunnel-client connect` is the supervisor for its profile. It listens on one Unix socket and answers two requests: `status`, with a redacted snapshot, and (since M0-03) `disconnect`; `tunnel-client status --config PATH [--json]` prints it and `doctor` reports whether it answered. `tunnel-client disconnect` sends the second (below). `credentials renew` (M0-07) does not use the IPC: see [Credential renewal](#credential-renewal). Source: `crates/tunnel-client/src/supervisor_ipc.rs`, wired in `main.rs` (`SupervisorPublisher`).

**Endpoint and lock.** `[supervisor] ipc_path` when set (relative to the profile's directory), else `supervisor.sock` in the directory holding the client key, which `credentials create` makes `0700`. This is the recommendation task row M0-03 recorded for its decision (1) -- options (c) with (a) as the default, Unix only, a new exit status for an absent supervisor -- applied by default pending owner confirmation on 2026-09-25 and **confirmed on 2026-09-28 as a coordinator decision under the owner's delegation** ("You work through the trade offs and make a decision"; M0-03 records the reasoning). **The profile lock is an exclusive non-blocking `flock` on `supervisor.lock`** beside the socket (the socket path with its extension replaced by `lock`), opened `O_NOFOLLOW` with mode `0600`, required to be a regular file owned by this user and closed to others, and held for the whole life of `connect`; the kernel releases it however the process ends, and the file is never removed. This replaced "the lock is the bind" after the M6-06 review (task row M6-C132): with only a connect-probe, two supervisors starting together could both find a stale socket, both unlink it and both bind. Probing, unlinking and binding the socket now happen only while the lock is held. **The lock fails closed:** another holder is `SUPERVISOR_RUNNING`, exit `9`, before a credential is read or a relay reached; a lock that cannot be trusted (a symlink, open to others, another owner, a directory others can write) is `IPC_UNAUTHORIZED`, exit `3`; any other failure to take it is `SUPERVISOR_LOCK_FAILED`, exit `9`. A socket nobody listens on (a SIGKILLed supervisor's) is replaced; one a live listener answers (a supervisor from before the lock) is `SUPERVISOR_RUNNING`. **Only the socket is optional:** with the lock held, a socket path longer than 103 bytes (the smaller of macOS's and Linux's `sun_path`) or one that cannot be bound leaves `connect` running without IPC, with one stderr line naming the code; `status` then reports no supervisor. **Not on Windows:** there is no supervisor IPC and so no profile lock there yet, and two `connect`s on one Windows profile are refused only by the relay (`OWNER_BUSY`). The two-socket invariant is untouched: this is a local Unix socket, not a device connection.

**Authorization: the same user, three ways.** The socket's directory must be owned by this user and not group- or world-writable, and the socket is `chmod 0600` after the bind. The server compares every accepted peer's kernel-reported UID (`SO_PEERCRED` on Linux, `getpeereid` on macOS, through `tokio::net::UnixStream::peer_cred`) with its own effective UID (`rustix::process::geteuid`, a safe call; no `unsafe` code) and closes any other peer without a byte, counting it in `ipc.peers_refused`. The reader refuses a socket that is not a socket, not owned by it, or reachable by group or others, and a listener whose peer UID is another user, so a socket planted by someone else cannot impersonate the supervisor. Every refusal is `IPC_UNAUTHORIZED`, exit `3`. Each connection is handled alone and bounded: a request of at most 64 bytes, a response of at most 64 KiB, 2 s for each exchange. Windows has no supervisor IPC or profile lock yet (`IPC_UNSUPPORTED`; `status` exits `2`), as credential creation already is Unix-only.

**What `status` reports** (`result`, schema version 1): `pid`; `state` (`starting`, `connecting`, `ready`, `backoff`, `stopping`); `device_id`; `sessions` that became ready; the reconnect `attempt` and `retry_delay_ms`; `last_error_code`, a closed diagnostic code and never a message; `certificate_expires_at_unix`; the configured `rotation_policy`; each export's `name` and `kind`; while a session is live, `session` -- phase, session ID, epoch, active and candidate generation and connection IDs, rotation ID, rotations completed, streams, open-journal entries, emitted and received sequence counts, drain fences and ACKs, queue and replay frames and bytes, recovery attempt and deadlines, and `open_refusals_sent` -- copied from the connector actor's bounded snapshot; and the IPC's own counters. **`session.open_refusals_sent` (M7-C168)** is the per-code count of OPEN refusals this session sent, the same object `connect --json` prints in `connect-status` ([Reconnecting `connect`](#reconnecting-connect), "Refusals the connector sent", M7-C167): one key per fixed code in `tunnel_protocol::open_refusal::CODES`, zeros included, counts only, per session. Plain `status` prints it as one `OPEN refusals sent: CODE=n ...` line naming the non-zero codes, and no line when all are zero. **It is additive within schema version 1, and absence means "not reported":** a supervisor from before M7-C168 omits the field; the reader (`status`, `doctor`) keeps it omitted, so `status --json` prints no `open_refusals_sent` for such a session rather than eight zeros that would read as "no refusals sent", and plain `status` prints `OPEN refusals sent: not reported by this supervisor`. A code this reader does not know, from a newer supervisor, is **dropped** rather than kept or refused: the label set is fixed, the snapshot stays readable, and a reader of that newer version reports it. Neither side needs a version bump, which is why none was made: the reader requires an exact `schema_version`, so a bump would make every older `status` refuse a newer supervisor. No consumer of this snapshot in the repository parses it with `deny_unknown_fields` (`SupervisorStatus` and `SessionStatus` do not). Tested by `supervisor_ipc::m7c168_tests` (the key set, the counts, no reason or category text, the round trip, an absent field staying absent, and an unknown code dropped). **Redaction is by construction:** no field can hold a path, an endpoint, a certificate or key, a ticket, a token, an export's canary, arguments or environment, or payload bytes. `crates/tunnel-client/tests/ops_gate_cli.rs` plants a canary in each of those places in a profile a live supervisor holds in memory -- the credential directory's name, the relay URL's path, an echo export's device canary, a stdio MCP export's arguments and environment, a Streamable HTTP MCP export's URL and bearer token file, the certificate's subject -- plus the key's and certificate's PEM bodies, and requires `status` and `doctor`, with and without `--json`, and `connect`'s own output to carry none; `scripts/m0-guard-exit-codes.py`'s `m6-06-ops-gate` suite copies the relay URL and an export's configuration into the snapshot in turn and requires that test to redden.

**`disconnect` (M0-03; coordinator decision under the owner's delegation, 2026-09-28).** `tunnel-client disconnect --config PATH [--json] [--timeout SECONDS]` connects exactly as `status` does -- the same socket-file checks and the same peer-UID check -- and sends `disconnect`. The supervisor answers with its snapshot as it stood (so `disconnect` learns the pid) and delivers **one stop request into the path SIGINT and SIGTERM already take** ([Stopping `connect` and `serve`](#stopping-connect-and-serve)): before the session is ready or while waiting to reconnect it exits `130` naming `disconnect`, with a live session it drains within `rotation.handshake_timeout_seconds + rotation.overlap_seconds`, prints `stopped` with `"signal":"disconnect"` and exits `0`, and a second request (or signal) during that stop exits `130` at once. There is deliberately **no second drain policy**: `--timeout` (default `30`, `1`--`3600` whole seconds, `30s` accepted) bounds only how long the command waits for the supervisor to stop answering on its socket, which it does only after its drain and child reap; on success it prints `state: stopped` with the pid and the time waited, exit `0`. A timeout is `5` `DEADLINE_EXCEEDED` and leaves the supervisor stopping. **Why this grants nothing new:** by default the socket sits beside the client key, in the credential directory `credentials create` makes `0700`, and the server admits only its own UID, so anyone who can reach the socket can already read the client's private key -- a far larger capability than stopping the supervisor. (A configured `[supervisor] ipc_path` elsewhere must be in a directory owned by this user and writable by no one else, and the socket itself is `0600`; the peer-UID check applies either way.) **Not retryable:** every `disconnect` failure reports `retryable: false` -- nothing running needs no retry, and a second request after one that may have been delivered is a second stop request, which abandons the drain and exits `130`; the timeout message says so. **A restarted profile ends the wait:** if a supervisor with another pid answers while `disconnect` waits (a service manager restarted it), the command exits `9` `SUPERVISOR_RUNNING` naming both pids; a socket refusal other than a supervisor closing mid-shutdown ends the wait with `3` `IPC_UNAUTHORIZED`. The IPC counters gain `disconnects_requested`, additive within schema version 1 (an older supervisor omits it, read as `0`); a supervisor from before M0-03 answers `disconnect` with `IPC_BAD_REQUEST`, which `disconnect` reports as `1` `PROTOCOL_ERROR`. With the example unit's `Restart=on-failure` and `SuccessExitStatus=130`, a disconnected service stays stopped. Source: `DISCONNECT_REQUEST` in `supervisor_ipc.rs`, `run_disconnect` and `StopSignal::Disconnect` in `main.rs`.

**Exit statuses.** `disconnect`: `0` stopped; `2` bad invocation or configuration; `3` `IPC_UNAUTHORIZED`; `9` `SUPERVISOR_RUNNING` when another supervisor answers while waiting; `5` `DEADLINE_EXCEEDED` when the request is not answered in 2 s or the supervisor has not stopped within `--timeout`; `8` `SUPERVISOR_ABSENT`; `1` `PROTOCOL_ERROR` for a malformed answer or a supervisor that does not know the request; `4` `TRANSPORT_ERROR` for any other local socket failure. `status`: `0` answered; `2` bad invocation or configuration; `3` `IPC_UNAUTHORIZED`; `5` `DEADLINE_EXCEEDED` when the supervisor does not answer in 2 s; `8` `SUPERVISOR_ABSENT`; `1` `PROTOCOL_ERROR` for a malformed answer; `4` `TRANSPORT_ERROR` for any other local socket failure. `connect`: `9` `SUPERVISOR_RUNNING` for a held profile, `9` `SUPERVISOR_LOCK_FAILED` or `3` `IPC_UNAUTHORIZED` for a lock it cannot take, otherwise as before.

**Measured** on the real binary, with no relay (the profile's relay is a refused port, so the supervisor stays in its reconnect loop): the socket's `0600` mode; `status` and `doctor` against a live supervisor; a second `connect` refused `9` while the first keeps answering; two `connect`s started together over a stale socket, ten rounds, leaving exactly one supervisor; a lock file that is a symlink stopping `connect` with `3` before it binds; a socket `chmod 0666` refused `3` by `status` and reported `failed` by `doctor`; a SIGKILLed supervisor's stale socket read as `8` and replaced by the next `connect`; the socket removed by an orderly stop; `disconnect` stopping a supervisor in its reconnect wait (`0` for `disconnect`, `130` naming the request for the supervisor, socket removed, `status` then `8`) and finding none (`8`); and every subcommand's exit statuses (`crates/tunnel-client/tests/ops_gate_cli.rs`). **`disconnect` against a live, ready session is not measured at the process level** -- it needs a relay -- and rests on that request entering the same select as SIGTERM, whose live-session stop is measured by the M1 harness's CLI smoke. The peer-UID check needs a second user, which a test process does not have, so it is held below the process level: `supervisor_ipc`'s unit tests drive the real `peer_cred` path with the expected UID shifted, in both directions. **Not measured:** a real second user, Windows, and a `connect` whose socket directory disappears while it runs.

## Credential renewal

**Implemented (M0-07), as decided in task row M0-03 (3)(a)** by the coordinator under the owner's delegation: a two-step local renewal, because the supported profile has an external issuer and no issuer protocol, and this reuses `credentials import`'s verified checks. Source: `crates/tunnel-client/src/renewal.rs`, wired in `main.rs` (`run_renew`, `pin_credentials`). Unix only, as `credentials create` and `import` are; elsewhere it exits `3` naming the platform.

1. **Request.** `credentials renew --config PATH --csr-out PATH` requires a valid current pair (key and certificate match), writes a new key to `<key>.renew-pending` beside the current key -- mode `0600`, `create_new`, synced, in the key's directory, which it makes `0700` -- and the CSR (subject `device/<device_id>`, as `credentials create` writes). The current key and certificate are not opened for writing. An existing CSR path, or one naming a profile credential file, is refused before anything is written. **A pending key is never replaced silently** (`RENEWAL_PENDING`, `2`, naming when it was written): the issuer may already hold its CSR, and a certificate issued for it matches only that key. `--discard-pending` removes it first, deliberately.
2. **Issue.** The operator carries the CSR to the external issuer. Nothing is locked meanwhile; `doctor` reports `renewal.status = pending` and when.
3. **Complete.** `credentials renew --config PATH --certificate PATH` reads the issued file once and makes `credentials import`'s checks against the **pending** key: X.509 v3, its public key the pending key's, this profile's device role SAN, not past `notAfter` (a `notBefore` still ahead is installed and warned about, as import does). It adds one check import cannot make: the certificate must come from **the issuer of the current certificate**, the issuer the relay has been accepting -- the same issuer name, the same authority key identifier when the current certificate carries one, and, when the current certificate file also carries its issuer (a chain of two or more), a chain that verifies to those certificates with rustls's own client-certificate verifier. The profile's configured server trust must still load. A refusal is `CREDENTIAL_ERROR`, `3`, and leaves the current pair byte-for-byte and the pending key in place for a retry. Re-running a completed renewal with the same file answers `already_installed` rather than refusing.

**The swap is crash-safe by order, not by atomicity.** Two files cannot be replaced together, so the steps are ordered so that every state a kill can leave is a valid pair or one recovery resolves without input: the issued chain is written to `<cert>.renew-staged` and synced; an older `<file>.renew-previous` pair is removed; the current key and certificate are hard-linked to `<file>.renew-previous` (a copy where there are no hard links); `rename(<cert>.renew-staged, <cert>)`; `rename(<key>.renew-pending, <key>)`; each rename followed by a directory sync. Only a kill between the two renames leaves a mismatched pair at rest -- the new certificate with the old key, the new key still pending -- and recovery renames the pending key into place (`rolled_forward`). Recovery runs, under an exclusive `flock` on `<key>.renew-lock`, at the start of every `credentials renew` and of `connect` (after the profile lock, before the first attempt; only when a renewal left something behind, so a profile never renewed creates no lock file). `doctor` reports the state (`interrupted`) without changing it. A failed (not killed) second rename puts the previous certificate back at once. The kept `.renew-previous` pair is one generation, for a manual rollback. Every holder keeps the lock for a few file operations; a second waits at most 5 s, then exits `7` `RENEWAL_LOCKED`.

**A running supervisor keeps its pair until it is stopped and started.** Before M0-07 `connect` re-read its three credential files for every session and every data-socket rotation, so a pair replaced on disk would have been picked up piecemeal at the next rotation -- the data socket presenting a different certificate from the control socket -- and a read between the two renames would have paired the new certificate with the old key. `connect` now reads the files once when it starts and uses those bytes for the life of the process (`CredentialConfig::pin`); it uses the new pair after `disconnect` (or the service manager) and a start. The completion output says so (`restart_required: true`).

**The relay half is not part of this command.** A renewal makes a **new key**, and the relay resolves a device's credential by its SPKI in the catalog, which no shipped command can yet extend with a new credential for an existing device (task rows M6-C31 and M6-C56). So after a restart the relay refuses the renewed pair (`CREDENTIAL_ERROR`, the M6-C32 identity refusal) until the catalog holds a credential for the new key; the kept `.renew-previous` pair is the way back meanwhile. End-to-end renewal therefore still waits on M6-C56's relay command, and the operator guide's known limitation stands.

**Output.** `--json` prints `{"schema_version":1,"command":"credentials renew",...}`: on a request `state: pending`, `discarded_pending`, `recovered`; on a completion `state: renewed`, `certificate_count`, `not_before_unix`, `not_after_unix`, `not_yet_valid`, `already_installed`, `recovered`, `restart_required`. No path, key or certificate body is printed in either mode's diagnostics; text mode names the CSR path the operator gave. **Exit codes:** `0`; `2` for a bad invocation, `RENEWAL_PENDING`, `RENEWAL_NOT_PENDING`, or a layout rename cannot renew (key and certificate in one file, or a symbolic link: `CONFIG_ERROR`); `3` for every credential refusal; `7` for `RENEWAL_LOCKED` (retryable).

**Evidence.** `renewal.rs` unit tests (each refusal, the stale-pending rule, modes, the lock, and a swap stopped after each of its seven steps then recovered); `tests/renew_cli.rs` on the real binary (each exit, the redaction canary, a debug build **aborted** after each step by `TUNNEL_CLIENT_TEST_RENEW_ABORT_AFTER` -- compiled only with `debug_assertions` -- then `doctor` and `connect` on the result, and a running `connect` that keeps its pair); `scripts/m0-guard-exit-codes.py` suite `m0-07-renewal`. Not covered: a real relay accepting the renewed pair after a restart, which it cannot until M6-C56 (above); the M1 harness exercises import, not renewal, a power loss rather than a process kill (the directory syncs are what that relies on, and nothing here cuts power), and a filesystem without hard links (the copy fallback is not exercised).

## Debugging and deployment contract

Each transition emits a structured event with stable event name, reason code, previous/next state, duration/deadline, and applicable IDs: trace/request, tenant, device, credential fingerprint, relay, cluster incarnation, owner epoch, socket generation, stream, and operation. Store opaque identifiers under log-access policy; never add high-cardinality IDs as metric labels. Validate incoming trace context and generate trusted internal IDs when absent or malformed.

`status` provides current state, owner/epoch, active/candidate/draining connection IDs and generations, certificate expiry, negotiated rotation policy, last successful rotation, retry deadline, last typed error, queue/replay/drain byte counts, pending per-direction/per-stream drain watermarks, absolute drain/overlap deadlines, stream count, and redacted export capability names. A bounded detail option lists stream watermark progress with a truncation indicator when the snapshot budget is reached. Snapshots come from the actor through a bounded request, so they describe one consistent state. They must not include raw certificate chains, environment values, endpoint query strings, file paths/content, prompts, screenshots, tool arguments, enrollment codes, tickets, or tokens.

Metrics cover connection/authentication failures by bounded reason, rotation duration/outcome, overlap time, queue occupancy, credit stalls, peer RTT, request latency, denied admission, and unknown outcomes. The relay delivers a minimal subset of this contract on an opt-in private listener (`metrics_bind`, M6-C24; [operator.md section 5](operator.md#5-metrics-logs-and-audit-retention) lists the series and what is not yet measured). Separate readiness from liveness: a process can be alive but unable to serve because trust, Redis authority, or owner routing is unavailable. Public health output exposes only readiness; detailed state is restricted administration data. **Readiness causes (M0-03; coordinator decision under the owner's delegation, 2026-09-28).** `/readyz` stays a bare `ready`/`unready`. The *why* is administrative data and lives on the private metrics listener (`metrics_bind`, loopback or private only), which already carries each single-relay readiness input with a fixed-label cause -- `tunnel_relay_authority_ready` with `tunnel_relay_authority_check_failures_total{class}`, `tunnel_relay_clock_offset_ready` -- and now carries a cluster relay's post-bootstrap signed-membership state too: `tunnel_relay_membership_readiness{state}`, one sample per fixed code (`starting`, `ready`, `unknown_authority`, `checkpoint_expired`, `catalog_unavailable`, `membership_rejected`, `missing_local_membership`, `missing_local_key`, `persistence_unavailable`, `cancelled`), exactly one of them `1`. The codes are `MembershipUnreadyReason::code()`, the same words `serve` prints when bootstrap fails, so a cause is named one way before and after bootstrap. This was chosen over the three options M0-03 listed (a local admin socket, an operator mTLS endpoint, a log line per transition) because it adds no listener and no authorization surface and reuses a closed-label channel an operator already scrapes; a relay without `metrics_bind` still has no post-bootstrap cause, which is the operator's choice.

Logs and optional local diagnostic bundles contain redacted configuration structure, build/protocol versions, dependency fingerprint, clock/expiry health, limits, and bounded recent state events. Use synthetic payload tracing only in dedicated test fixtures. Payload logging and TLS session-key logging stay disabled in production, including debug mode. Sampling and retention budgets are configuration, not unbounded file growth.

Every peer fault a relay observes while dispatching to a remote owner, or while serving a forwarded request as the owner, is published on the relay's typed snapshot as one bounded `peer_fault_diagnostics` tuple: a role (`ingress` or `owner`), a stage from the closed dispatch order `validation`, `pool_connect`, `stream_permit_checkout`, `sender_lock`, `h3_dispatch`, `envelope_send`, `complete`, `head`, `body`, `lease`, `owner`, and a closed cause label (for example `no_live_owner`, `identity_mismatch`, `transport_goaway`, `transport_h3`, `transport_timeout`, `transport_pins_unavailable`, `membership_expired`, `owner_not_ready`, `rotation_freeze`, `capacity`, `remote_unauthorized`, `deadline`). `rotation_freeze` is the owner's scheduled data-rotation freeze outlasting its bounded admission hold, or a full hold (M3-15). It is kept apart from `owner_not_ready`, the owner's fault states, because the consumer's answer differs: `ROTATION_FREEZE` rather than `PEER_UNAVAILABLE`. `transport_pins_unavailable` is its own cause rather than a generic authentication failure because it means this relay publishes no approved peer trust evidence at all: no socket was opened and no peer certificate examined, so the consumer is answered `not_dispatched` with a bounded retry hint instead of an unknown outcome. The tuple carries only correlation identifiers: tenant, device, session, owner epoch, owner node, service and request identifiers. Transport error text, payloads, bearer tokens, endpoints and paths never enter it. Each request records at most one tuple, and an owner-side handler records it before the owner registration it refers to is closed, so a fault outlives the state it describes. The snapshot retains saturating stage and cause counters, the latest tuple per stage and a ring of the thirty-two most recent tuples. An owner admission decision (`owner_not_ready`, `rotation_freeze`, `capacity`, a remote status) observed by the ingress while waiting for the response head is attributed to the `owner` stage; a transport failure at the same point stays at `head`. The `verify-m7-c11-diagnostics` matrix parses every captured relay snapshot strictly against this schema and requires exact tuples where the induced fault implies them, and `verify-m7-og02-correlation` reports the tuples and correlation families each fault gate produced.

Public consumer HTTPS may terminate at an explicitly configured reverse proxy; its upstream channel must be protected and forwarded host/proto values accepted only from configured proxy addresses. The device mTLS listener initially requires direct TLS termination inside the relay or **layer-4 TCP passthrough**. A generic HTTP proxy that replaces device TLS with its own upstream connection cannot preserve the required mTLS identity through arbitrary headers.

Peer HTTP/3 requires bidirectional private UDP reachability and QUIC support through the actual load-balancer/firewall path. A successful HTTPS health check does not prove it. Peer credentials and node identity terminate at the participating relay, not an unrelated public proxy. No silent HTTP/2 fallback is permitted in the initial cluster profile. Configure and test UDP idle timeouts, maximum streams, connection/stream windows, keepalive, and graceful draining against the deployment path.

## Error and incident vocabulary

Keep transport failures, authentication decisions, admission, and application outcomes distinct. A TLS failure may happen before an HTTP request exists; it produces a local diagnostic and handshake metric, not a fabricated HTTP response or application operation ID.

| Typed category | Example diagnostic | Operator interpretation |
| --- | --- | --- |
| `TlsTrust` | `SERVER_CERT_UNTRUSTED`, `DEVICE_CERT_EXPIRED` | Verify trust bundle, role, expected name, expiry, and clock; never suppress verification |
| `DeviceAdmission` | `DEVICE_CREDENTIAL_REVOKED`, `DEVICE_DISABLED` | Resolve the durable credential/policy record through an authorized administrator |
| `Pairing` | `DATA_TICKET_USED`, `DATA_KEY_MISMATCH` | Diagnose attachment/epoch/credential lifecycle; a retry needs a fresh authorized ticket |
| `PeerAdmission` | `PEER_KEY_UNAPPROVED`, `PEER_TRUST_STALE` | Inspect signed membership and node identity; public HTTPS health is unrelated |
| `Ownership` | `OWNER_FENCED`, `AUTHORITY_UNAVAILABLE` | Follow cluster recovery; never manually copy an old epoch into a new process |
| `Capacity` | `STREAM_LIMIT`, `QUEUE_BUDGET_EXCEEDED` | Work was refused before dispatch; return a bounded retry hint |
| `Rotation` | `CANDIDATE_TIMEOUT`, `DRAIN_TIMEOUT` | Inspect connection IDs, watermark gaps, credit stalls, and the absolute overlap deadline |
| `Adapter` | `ADAPTER_UNAVAILABLE`, `OUTCOME_UNKNOWN` | Distinguish failure before dispatch from an operation that may have executed |

The codes above are proposed public vocabulary, to freeze with the error-schema implementation.

**Session close reasons that look alike and mean different things (implemented).** The relay records why it closed a device session in its `session_closed` log line (`reason`) and its bounded session terminal diagnostics, and sends the same code to the device in a `REJECTED`. Three of them concern the data carrier and are easy to confuse:

| Close reason | Meaning | Operator interpretation |
| --- | --- | --- |
| `REVERSE_CHANNEL_UNAVAILABLE` | A frame for the device could not be queued because the data carrier's receiver is gone: the device's data socket has ended | Treat as a lost device transport; the connector reconnects or recovers |
| `FLOW_CONTROL_UNDELIVERABLE` | A relay `ACK` refused by a **live** carrier (budget or slots) stayed owed while the carrier took none of the owed `ACK`s for 5 s: the relay's own backpressure outlasted the retry window (task rows M4-37, M6-C160). A single refusal no longer fences; it is retried. An owed `ACK` whose carrier closes is dropped silently: carrier loss is detected on its own path and unacknowledged frames replay | The device was healthy. Look at the session's queue diagnostics (`queue_bytes_high_water`, `data_queue_depth_high_water`, `data_queue_refusals`) for a consumer or carrier that stopped draining; a unary echo consumer sees the same code in its 503 |
| `FLOW_CONTROL_OWED_LIMIT` | The session would have owed more relay `ACK`s at once than it can retain streams (`2 × max_streams_per_device × 2`, 256 at the defaults; review of #199, task row M6-C160). Every entry needs a retained stream, so a healthy session cannot reach this; it means the retention invariant broke | The device was healthy. Treat as `FLOW_CONTROL_UNDELIVERABLE`: look for a carrier that stopped draining |
| `CONTROL_CLOSED` | The device's control socket ended -- or its data socket's loss was processed first and retained recovery could not start because control had gone too (M4-49) | The device's transport ended on both sockets |
 Logs retain nested causes locally; external errors contain only the stable safe code, a short explanation, request/operation ID where available, and a permitted retry hint. Do not leak host paths or raw TLS/backend errors through consumer responses.

Initial runbooks should answer a bounded set of questions:

1. **A CLI cannot connect:** use local `doctor` to verify configuration and credentials, then `doctor --network` to distinguish DNS, server trust, device mTLS, and application admission. Never replace verification with a permissive TLS option during diagnosis.
2. **Control is up but data is absent:** inspect the selected owner, credential ID, ticket result, connection ID, and candidate deadline. Check both direct and forwarded attachment admission without printing a ticket.
3. **Rotation is draining:** inspect old-generation final sequence versus contiguous ACK for each pending stream direction, queued bytes, and remaining overlap time. Preserve the fixed deadline; a stuck adapter cannot keep the old socket alive forever.
4. **Only cross-node requests fail:** check peer UDP reachability and ALPN, then mutual certificate identity, signed key membership freshness, owner fencing, and bounded forwarding capacity in that order.
5. **A mutation disconnected:** query the authorized operation status. Report a known result or explicit ambiguity; neither reconnect nor a transport ACK authorizes repeating the mutation.
6. **Redis authority was lost or restored:** fail closed and follow the quiescence, verified-backup and externally approved new-incarnation process in [cluster.md](cluster.md); do not restart relays independently using a remembered lease or local catalog snapshot.

Each runbook must link a reproducible synthetic fixture and the expected event sequence before alpha release. Production debugging changes must not weaken authentication, increase unbounded buffers, or invoke a real desktop as a probe.

## Implementation and verification gates

1. **TLS identity spike:** direct device mTLS on both WSS endpoints, certificate extraction into typed Axum identity, custom client rustls configuration, and two sockets plus one bounded candidate. Prove no certificate, wrong issuer, expired certificate, wrong role, unknown/revoked device, stolen ticket, wrong key, and forged identity headers fail before dispatch.
2. **Peer stack spike:** two real processes negotiate HTTP/3 over UDP with mutual certificates, verify allowed identities/keys, exchange bounded streaming request/response bodies, cancel streams, and reject missing/wrong-role/unapproved peers. Pin the compiled dependency set and document tested platforms; no business adapter is required yet.
3. **CLI contract:** snapshot help and versioned JSON, test all exit-code mappings and flag precedence, exercise credential create/import with fixture PKI, enforce key-file/IPC permissions, and prove `config check`, `status`, and default `doctor` do not open tunnels or invoke exports.
4. **Lifecycle:** deterministic model/property tests for rotation, concurrent requests, bounded queues, cancellation, credential renewal, expiry, and task shutdown. Fake time and injected failures must reproduce every state transition and ambiguous-operation result without wall-clock sleeps.
5. **Real deployment:** test public OAuth HTTPS and device mTLS WSS through supported proxy arrangements, plus private HTTP/3 across three relays. Prove both socket admissions preserve identity when they reach different nodes; inspect actual ALPN/TLS/peer identity rather than infer success from an HTTP response.
6. **Debuggability:** a fixture trace reconstructs an authorized request through ingress, owner, CLI, adapter, and result across rotation; induced failures identify the responsible layer. Automated redaction checks scan logs/status/bundles for planted secrets and payload markers; pressure tests verify diagnostic paths stay bounded.
7. **Provisioning release gate:** selected issuer and renewal profile, atomic enrollment receipt behavior, short-lived one-use authorization, role separation, revocation cutoff, expired open-session closure, and recoverable interrupted credential replacement are tested before self-service enrollment is shipped.
